## 1. 全体構成

```
┌──────────────────────── Windows PC（常時稼働） ────────────────────────┐
│ barnull（Python 1プロセス、asyncio）                                       │
│                                                                            │
│  ┌ 管理画面ポーラ（5分±1分）┐  ┌ Slack（Bolt, Socket Mode）┐             │
│  │ SM 受信トレイ / IB 予約・ │  │ reaction_added / message  │             │
│  │ メッセージ一覧 → 差分検知 │  └─────────────┬─────────────┘             │
│  └──────────┬───────────────┘                │                            │
│             ▼                               ▼                              │
│        ┌──────────── ワークフロー（状態遷移・排他・冪等） ────────────┐    │
│        │ 予約 / 問い合わせ / 利用完了 / 例外                         │    │
│        └───┬──────────────┬──────────────┬─────────────┬─────────────┘    │
│            ▼              ▼              ▼             ▼                   │
│      SQLite(WAL)    Playwright（SM・IB    Claude API   APScheduler          │
│      data/barnull.db  の管理画面を操作）  （分類・文案）（リマインド・      │
│                       data/browser/*                   ポーリング・完了判定）│
│                                                                            │
│  見張り: 死活通知（Slack の予約投稿を使ったデッドマンスイッチ）、          │
│          スリープ抑止（SetThreadExecutionState）                           │
└────────────────────────────────────────────────────────────────────────────┘
```

- 1プロセスの中で、Slack イベント、管理画面のポーリング、スケジューラを asyncio で並行に動かす
- ブラウザ操作はプラットフォームごとに1本のキューで直列化する（同時に2画面を操作しない）
- **ブラウザ操作は決定的なスクリプトだけで行う。** LLM には画面を操作させない
- LLM の用途は4つ（返信の意図分類、問い合わせ判定、返信文案、お礼文）。送信する文面は承認された文字列をそのまま使い、送信の直前に作り直さない

### 1-2. 常駐のさせ方（Windows）
- `scripts/install_task.ps1` がタスクスケジューラに `BarNullOps` を登録する
  - トリガー: PC 起動時（ログオンしていなくても実行）＋念のため 5 分ごとの起動チェック
  - 操作: `uv run barnull run`（多重起動はロックファイルで防ぐ）
  - 失敗時: 1分後に再起動、回数無制限
  - 「ログオンしていなくても実行」にするには Windows のパスワード入力が必要。登録はご本人が実行する
- スリープ: プロセス稼働中は `SetThreadExecutionState` でスリープを抑止する。加えて、電源設定で「スリープしない」にするのはご本人の作業（runbook に手順）
- **PC 自体が止まった時の検知**: Slack の予約投稿（`chat.scheduleMessage`）を使ったデッドマンスイッチ。プロセスが10分ごとに「30分後に投稿される⚠️停止警告」を予約し直し、前の予約を取り消す。プロセスや PC が止まると予約が取り消されず、30分後にチャンネルへ警告が出る

### 1-3. 秘密情報
Windows 資格情報マネージャー（`keyring`、サービス名 `bar-null-ops`）に保存する。登録は `uv run barnull set-secret <名前>` でご本人がターミナルに入力する（画面に表示しない）。

| 名前 | 内容 |
|---|---|
| `SLACK_BOT_TOKEN` / `SLACK_APP_TOKEN` | xoxb- / xapp- |
| `ANTHROPIC_API_KEY` | Claude API |
| `KEYBOX_CODE` | キーボックス暗証番号 |
| `SM_EMAIL` / `SM_PASSWORD` | スペースマーケット |
| `IB_EMAIL` / `IB_PASSWORD` | インスタベース |

- ログ・action_log・Slack・スクリーンショットのファイル名に暗証番号とパスワードを出さない。ログ出力時に `KEYBOX_CODE` の値を `****` に置換するフィルタを入れる
- スクリーンショットは定型文送信後の画面に暗証番号が写る。`data/screenshots/` はローカルのみに置き、Slack には失敗時の画面だけを上げる。送信完了の画面は上げない

## 2. 入力（トリガー）

### 2-1. 通知メールは使わない
- Google Cloud の OAuth クライアントを作れないため、Gmail は読まない（2026-10-09 回答）
- 代わりに管理画面のポーリング（§2-2）がすべての検知を担う。検知の遅れは最大で約6分
- 将来メール連携を足す場合に備え、調査結果（§2-3）とメールのフィクスチャは残しておく。IMAP（アプリパスワード）なら Google Cloud が不要なので、Workspace の設定で許可できれば後から追加できる

### 2-2. 管理画面のポーリング（5分 ± ジッター1分。唯一の検知手段）
| 対象 | 見るもの | 目的 |
|---|---|---|
| SM 受信トレイ一覧（1ページ目、メッセージ更新日順） | 行ごとの予約ID・ステータス・日時・金額。一覧を取る API の JSON（更新日時・未読など）を `page.on("response")` で受け取れればそれも使う | 新しい予約リクエスト・問い合わせ、ステータス変化（予約完了・キャンセル・期限切れ・利用完了）、**行の内容や並び順の変化＝新着メッセージの可能性** |
| SM の該当スレッド（一覧で変化があった行、利用終了を過ぎた予約、保留中・文案待ちの予約） | ステータス、最後のホスト発言より後のゲスト発言、退室時状態の記録、変更リクエスト・延長 | 新着メッセージ（F4）、利用完了（F6）、変更・延長（F8） |
| IB 予約一覧（予約日時の新しい順） | 予約ID・ステータス・ゲストID | 新しい予約、キャンセル |
| IB メッセージ一覧（未返信のみ）と、ヘッダの未読件数 | `message_filter[unreplied]`、`未読 N 件` | 新着メッセージと返信漏れ（F4）、変更リクエスト |
| IB の該当予約詳細・スレッド | 予約状況、清掃終了時刻、スレッドの発言 | 状態確認、利用完了の時刻 |
| 保留中・未送信文案のある予約 | 状態の確認 | 手動対応の検知（F3 の停止条件） |

- 管理画面を開くのは「一覧1ページ＋変化のあった行だけ」にし、アクセスを増やしすぎない（1回の巡回で SM・IB とも一覧2〜3画面＋変化分）
- 一覧の各行の「前回の見え方」を DB（`listing_snapshots`）に持ち、差分があった行だけ詳細を開く
- 予約リクエストは届いてから最大約6分で通知される。SM の承認期限やゲストの待ち時間に対して十分短い
- 稼働中＝ CLOSED でない予約・問い合わせ。CLOSED 後もゲストが書き込めば一覧の並び順で拾う

## 3. 状態遷移

### 3-1. 予約（reservations.state）

```
            ┌──────(保留の返信)──────┐
            │                        ▼
NOTIFIED ──(承認スタンプ)──▶ EXECUTING ──▶ CONFIRMED ──(利用完了の判定)──▶ COMPLETING ──▶ CLOSED
   ▲            ▲   ON_HOLD ──(スタンプ)──┘   │  ▲                           │
   │            │     │ 4時間ごとにリマインド  │  │                           ├─(退室に問題あり)─▶ REVIEW_CONFIRM ─(スタンプ)─▶ COMPLETING
   │            │     └─(手動対応を検知)──▶ CONFIRMED                        │
   │            └──(再実行スタンプ)── ERROR ◀─(失敗)─┘                        └─(失敗)─▶ ERROR
任意の状態 ──(キャンセル・否認・期限切れ)──▶ CLOSED
CLOSED ──(ゲストから新着メッセージ)──▶ 問い合わせを作成（予約は CLOSED のまま、Slack スレッドで再開）
```

| 状態 | 意味 | 親メッセージの表示 |
|---|---|---|
| NOTIFIED | 通知済み。承認待ち | 🟡 承認待ち |
| ON_HOLD | 保留中（4時間ごとにリマインド） | ⏸ 保留中 |
| EXECUTING | 承認・定型文送信の実行中 | ⏳ 実行中 |
| CONFIRMED | 定型文とマニュアルの送信済み | ✅ 送信済み（未送信の文案があれば 💬 返信待ちあり） |
| COMPLETING | レビュー投稿の実行中 | ⏳ 完了処理中 |
| REVIEW_CONFIRM | 退室に問題あり。レビュー投稿の確認待ち | ⚠️ 要対応 |
| ERROR | 自動処理が失敗 | ⚠️ 要対応 |
| CLOSED | 対応完了／キャンセル | 🏁 対応完了 ／ ✖️ キャンセル |

- IB は即時予約なので「承認」の操作が無い。スタンプで定型文と PDF を送る
- 遷移は `UPDATE … SET state=? WHERE id=? AND state IN (…)` の比較更新で行い、更新件数が 0 なら他の処理が先に動いたとみなして何もしない（同時スタンプの二重実行防止）

### 3-2. 問い合わせ・返信文案（inquiries.state）

```
DRAFT_POSTED ──(スタンプ／修正文案)──▶ SENDING ──▶ SENT
     │  ▲                                  └─(失敗)─▶ ERROR ─(再実行スタンプ)─▶ SENDING
     │  └──(新しい文案で置き換え)──┐
     ├──(保留の返信)──▶ ON_HOLD（4時間ごとにリマインド）─(スタンプ／修正文案)─▶ SENDING
     ├──(管理画面でホストの返信を検知)──▶ SENT_MANUALLY（送信しない）
     └──(【要確認】が残ったままスタンプ)──▶ 送らずに修正を依頼（状態は変えない）
```

- 予約に紐づくもの（予約前の問い合わせ・予約時の質問・予約後のメッセージ）と、予約に紐づかない SM の予約前問い合わせがある。後者は「問い合わせ」の親メッセージを作る。同じゲストがその後予約したら、予約通知をその Slack スレッドに続けて投稿する
- 予約時に質問を含む場合は、予約の承認スタンプで定型文、文案のスタンプで問い合わせ返信を送る。両方承認済みなら定型文 → 問い合わせ返信の順に送る（定型文の送信前に文案を承認しても、定型文の後まで待たせる）

## 4. 機能ごとの処理

### F1. 予約受領通知
1. ポーリングで新しい予約（SM の「予約リクエスト」行、IB の予約一覧の新しい行）を見つける。`(platform, 予約ID)` が既にあれば何もしない
2. 予約詳細の画面を開いて項目を取る（日時、ゲスト名、人数、利用目的・用途詳細、オプション、料金明細、店舗収益、IB のゲストID・準備・清掃時間、SM のリクエスト本文と現在のステータス）。店舗収益が取れない場合は合計と手数料率で通知し、後で取れたら親メッセージを更新する
3. リピート回数: `guest_history` から、同じプラットフォームの同じゲストの過去予約（キャンセルを除く、今回を除く）を数える。IB はゲストID、SM はゲストID が取れなければ氏名の正規化（「様」「さま」・空白・全角半角の違いを除く）で照合
4. 親メッセージを投稿し、`ts` を保存する（Block Kit。§5）
5. 予約リクエストの本文・用途詳細・最初のメッセージに質問や相談が含まれるかを Claude で判定し、含まれる場合は F4 の文案をスレッドに続けて投稿する

### F2. 承認スタンプ → 定型文とマニュアルの送信
対象: 親メッセージ（または保留リマインド、再実行ボタン付きのエラー）への承認者のスタンプ

**SM**
1. 状態を NOTIFIED/ON_HOLD/ERROR → EXECUTING に比較更新（失敗なら終了）
2. スレッドを開き、ステータスを読む
   - 「承認」ボタンがある → 押す → 確認モーダルの「承認」を押す → システムメッセージ「予約ステータスが「承認」になりました」を確認
   - 既に承認済み・予約完了 → 承認はスキップ
   - キャンセル・否認・期限切れ → 送らずに CLOSED、Slack に報告
3. 送信前チェック: ホスト側の発言に「キーボックスの暗証番号」を含むテキストと PDF が既にあるなら送らない（手動送信済みとして報告）
4. 定型文を入力して「送信」→ 自分の発言として表示されたことを確認
5. PDF をファイル入力に設定 → 確認モーダル「送信するファイルに間違いはありませんか？」で送信 → `SendFileSelf` にファイル名が出たことを確認
6. 送信後の画面で、定型文と PDF の両方が表示されていることを確認してから CONFIRMED。スレッドに「✅ 承認・送信しました（スタンプ: ◯◯ / 時刻）」、親メッセージを更新

**IB**
1. 比較更新で EXECUTING
2. 予約詳細を開き、予約状況を読む（キャンセル済みなら CLOSED）。「予約リクエスト中」なら「承認」「承認する」のボタン（「承認しない」「非承認」は押さない）で承認し、確認ダイアログは OK。承認後に予約状況が変わったことを確認
3. メッセージ欄: スレッドがあれば `threadPath` へ、無ければ「スレッドを作る」ボタンで作る（スレッドIDを `reservations.ib_thread_id` に保存）
4. 送信前チェック: この予約の確定時刻より後に、ホストの発言で「キーボックスの暗証番号」＋PDF があれば送らない
5. 本文に定型文、ファイルに PDF を設定して1回で送信 → 両方表示されたことを確認 → CONFIRMED

**定型文**（`config.toml` の `template.reservation`。`{SALUTATION}` と `{KEYBOX_CODE}` だけを差し込む）
- `{SALUTATION}` は「<名字>さま」＋空行。名字は予約者名の最初の空白（全角・半角）より前。空白が無い・英字のイニシャルだけ等で名字が分からない時は宛名なし（空行も入れない）
```
{SALUTATION}ご予約ありがとうございます！
ご利用マニュアルを添付いたしますので、当日はこちらをご参照いただけますと幸いです。
なお、当日のキーボックスの暗証番号は【{KEYBOX_CODE}】となっております。

ご不明点等ございましたらお気軽にご連絡くださいませ。
よろしくお願いいたします！
```

### F3. 保留とリマインド
- 予約の Slack スレッドに承認者が返信したら、Claude で意図を分類する（JSON で返させる）

| 分類 | 例 | 処理 |
|---|---|---|
| HOLD | 待って、確認します、一旦保留 | ON_HOLD。保留開始から4時間ごとにリマインド |
| REVISION | 修正後の文面の全文 | F5 へ |
| CANCEL_OR_DENY | 否認して、キャンセルして | **自動では実行しない。**「管理画面で手動対応をお願いします（URL）」と返信して ON_HOLD |
| OTHER | メモ、雑談 | 何もしない |

- リマインドのたびに管理画面を読み、次のどれかなら止める
  1. 承認者がリマインドか親メッセージにスタンプ → F2 を実行し、完了後に停止
  2. 「予約確定済み」かつ「定型文・マニュアル送信済み」→ 自動では送らず「手動対応を確認しました」と報告して CONFIRMED
  3. キャンセル・否認・期限切れ → 報告して CLOSED
- SM の予約リクエストには承認期限がある（期限切れで無効）。保留中に期限が近づいたら（残り12時間・3時間）リマインドに期限を明記する

### F4. 問い合わせの検知と返信文案
- 対象
  - 予約時: リクエスト本文・用途詳細・最初のメッセージに質問・依頼・相談がある（Claude で判定）
  - 予約後: ゲストの新着メッセージは**質問でなくても必ず**文案を作る（お礼・挨拶への返信も含む）
  - SM の予約前問い合わせ（一覧の「お問い合わせ」行）
- 検知: SM は受信トレイ一覧の変化 → スレッドを開いて読む。IB は「未返信のみ」の一覧と未読件数 → スレッドを開いて読む
- 未返信の判定: そのスレッドの最後のホスト発言より後にあるゲスト発言をまとめて1件の問い合わせにする。同じゲスト発言で2つ目の文案を作らない（`inquiries.source_key` に発言の時刻と本文のハッシュを持つ）
- IB はスレッドが「スペース×ゲスト」単位なので、新着は、そのゲストの予約のうち CLOSED でないもの（無ければ最も新しいもの）の Slack スレッドに投稿する
- 文案の材料: そのスレッドのやり取り全文、`knowledge/past_replies/`（過去のホスト返信）、`knowledge/manual.md`、`knowledge/faq.md`、予約情報
- 文案のルールは依頼書 §6 をプロンプトに入れる。根拠の無い事項は `【要確認: …】` にする。暗証番号は CONFIRMED の予約にだけ書いてよい（プロンプトには値を渡さず `{KEYBOX_CODE}` と書かせ、送信時に置換。置換前の文面を Slack に出す）

### F5. 文案の承認・修正
- 文案メッセージに承認者がスタンプ → その文案をそのまま送る
- 承認者がスレッドに修正後の全文を返信 → **一字一句変えずに**送り、「以下の文面で送信しました」と全文を引用して報告
- 次の場合は送らずに確認する:「この文面をそのまま送信してよければ、このメッセージにスタンプを」
  - 返信が修正文案か指示・コメントか判断できない（分類の確信度が低い）
  - 未送信の文案が2つ以上あり、どれへの修正か判断できない
- `【要確認: …】` が残った文案は、スタンプが付いても送らずに修正を依頼する
- 送信前チェック: 文案の作成後にホストの発言が増えていて、その中に同じ文面がある → 送らない
- 未送信の文案は4時間ごとにリマインドする

### F6. 利用完了とレビュー
- 利用完了の判定
  - SM: スレッド内の退室記録（「ゲストが退室時の状態を記録しました」）、または利用終了＋60分のうち早いもの（延長があれば終了時刻を更新）。利用終了を過ぎた予約はポーリングのたびにスレッドを見る
  - 退室時状態は「問題なく退室しました」か「気になる点があります」（＋種類・詳細）
  - IB: 清掃終了（無ければ利用終了）＋60分
- 処理
  1. 退室時状態が「問題なく退室しました」 → レビューを自動で投稿（★5・お礼文）。自動の投稿は CONFIRMED からだけ（人の指示・確認待ちを上書きしない）
     - SM: `/inbox/<予約ID>/review` で星を選び（選んだ数だけ緑になったかを確かめる）、コメント（10〜400字）、本文側の「レビューの投稿」→
       確認画面「公開後にレビューの編集はできません。レビューを投稿してよろしいですか？」の「投稿」。
       `POST …/owners/<host>/reservations/<ID>/reputation` の応答が 2xx なら成功（表示の反映が遅れても失敗にしない＝二重投稿しない）
     - IB: `/partners/bookings/<予約ID>/user_reviews/new` で評価、コメント、「レビューを投稿する」（確認画面なし）
  2. 退室時状態が「気になる点があります」、または利用終了から3時間たっても退室の記録が無い → REVIEW_CONFIRM（確認メッセージにスタンプで投稿）
  3. まだ書けない（SM の can_be_reviewed が false、IB の投稿前一覧に無い） → CONFIRMED に戻して後で再試行。3日続いたら REVIEW_ERROR で知らせる
- 投稿済みかの判定（2026-10-12 実画面で確認）
  - SM: スレッド画面が読む予約情報 `GET …/owners/<host>/reservations/<ID>` の `reputation_id_by_owner`（null＝未投稿）、
    `can_be_reviewed`（書けるか）、`review_expires_at`（期限）。レビュー画面の `GET …/reputation`（200＝投稿済み、404＝未投稿）でも確かめる。
    サイドバーの「ホストレビューあり」はゲストのバッジで、ホストの投稿の有無ではない。「レビューの投稿」ボタンは投稿後も公開まで残る
  - どちらも読めない（投稿済みか分からない）ときは投稿しない（REVIEW_ERROR）
  - IB: 「投稿済みのレビュー」一覧にあれば投稿しない
- 承認者の返信によるレビューの指示（スレッドへの返信）
  - はっきりした指示 = 60字以内（★N・評価・コメントで始まる指示のコメント「…」は数えない）・【 で始まらない・
    「★／レビュー／評価／コメント「」で始まるか、評価（★N・星N・N つ星・評価N・★★★・:star: の絵文字だけ）や「レビューしない」系の語を含む
    - ★N（コメント「…」）、コメント「…」だけ → 利用後なら確認メッセージ（スタンプで投稿）。利用前・利用中なら記録し、利用後に確認メッセージを出す（自動では投稿しない）
    - 「レビューしない」系 → 利用後なら投稿せずに CLOSED（期限内なら ★N の返信で再開できる）。利用前・利用中なら記録し、利用後に投稿せずに終える
    - レビューの文の「まだ」「一旦」「後で」「待って」「止めて」→ 保留（投稿しないと決めたのではない。確認待ちにする）
    - 違う評価が複数ある（「★5じゃなくて★3」）→ 推測せず、書き方を案内する
    - 同じ返信の、レビュー以外の文の「待って」「否認」も行う（「否認して。レビューもなしで」）
    - 投稿の処理中（COMPLETING）に来た指示（「待って」も含む）は記録するが、止められない可能性があることを返信で伝える。
      投稿が失敗したら記録した指示に従う（「レビューしない」なら再実行のスタンプを出さない、★N なら再実行の内容にする）
  - レビュー・評価・星に触れているが、はっきりしない返信 → 自動投稿を止め（利用後なら確認メッセージ）、返信は通常の扱い（修正文なら送信の確認）にも回す。
    それまでのはっきりした指示（「レビューしない」・★N）は、評価もコメントも読み取れない返信では上書きしない
  - 新しい指示は、それ以前に承認された内容より優先する。評価の指定が無い確認メッセージは、それまでの指示・承認済みの内容を引き継ぐ
  - 確認メッセージへのスタンプは、確認待ち（REVIEW_CONFIRM）の最新のメッセージだけ受け付ける。対応を終えた予約への ★N の返信には、何もしていないことを返事する
- 確認待ち・失敗（REVIEW_CONFIRM／REVIEW_ERROR）の間に SM の退室時状態に「気になる点」が記録されたら、スレッドに1回だけ知らせる（Slack に出せなければ定期処理で出し直す。投稿されたか分からない状態では出さない）。承認済みで書けるのを待っている内容も、その後に気になる点が記録されたら投稿せずに確認し直す
- 確認メッセージを出せなかった・出す途中で止まった場合は、出そうとした内容（評価・コメント・見出し）を記録しておき、出し直す
- 失敗時: REVIEW_ERROR。⚠️ メッセージに「再実行で投稿する内容（★N「コメント」）」を出す。再実行は最新の⚠️へのスタンプだけ受け付ける
- 二重投稿の防止: 管理画面の操作は、投稿の最後のボタン（SM 確認画面の「投稿」、IB「レビューを投稿する」）を押す直前に印を付ける（`review_submitted`）。
  印の後は、時間切れでも操作を途中で止めずに待つ。印の後に失敗・停止したら「投稿されたか分からない」として再実行のスタンプは出さず、
  管理画面を確かめてから ★N で返信してもらう（確認メッセージへのスタンプの時に、投稿済みならサイトの API で分かるので投稿しない）。
  サイトが受け付けなかった（SM の応答が 2xx 以外）ときは印を外す（再実行してよい）
- お礼文は Claude で作る（1〜2文。用途に軽く触れてよい。確認できない事実や氏名以外の個人情報は書かない）。自動で作ったお礼文は再試行でも同じものを使う
- 完了通知を投稿し、CLOSED（🏁 対応完了）
- 取りこぼし検知
  - IB: 「投稿前のレビュー」一覧を定期的に確認し、未投稿なら F6 を実行する
  - SM: 30分ごとに、14日以内に閉じた予約（キャンセル・投稿済み・「レビューしない」を除く）の予約情報を読み、未投稿で期限内のものを一覧で知らせる（自動では投稿しない）。
    読めなかった予約は6回まで再試行し、それでも読めなければ「確認できませんでした」として一覧に載せる

### F7. クローズ
- F6 の完了通知で CLOSED。以後リマインドしない
- CLOSED 後にゲストから新着があれば、同じ Slack スレッドで F4 から再開する（予約は CLOSED のまま、問い合わせだけ動く）

### F8. 例外
| 事象 | 処理 |
|---|---|
| キャンセル（ゲスト／ホスト）・否認・期限切れ | スレッドに通知して CLOSED |
| 予約変更（確定済み） | 日時・金額を更新してスレッドに通知。利用完了の判定に使う |
| **予約変更リクエスト（ゲストから、回答が必要）** | ⚠️ でスレッドに通知し、回答画面の URL を出す（自動回答はしない）。調査で、IB に未回答の変更リクエストが残っていたため追加 |
| SM の利用時間の延長 | 終了時刻を更新してスレッドに通知 |
| 対応漏れ（SM 一覧の「未返信」表示、承認期限の接近、問い合わせの期限切れ） | 該当スレッド（無ければチャンネル）に⚠️。承認者をメンション |
| 自動処理の失敗 | スレッドに⚠️（失敗した手順、エラー、画面のスクリーンショット）。承認者をメンション。「このメッセージにスタンプで再実行」。再実行前に必ず管理画面の状態を読み、二重送信を防ぐ |
| ログイン切れ | 保存済みの ID・パスワードで自動再ログイン。失敗、2段階認証、CAPTCHA、規約同意の画面が出たら操作を止めてチャンネルに⚠️（同じ警告は1時間に1回まで） |
| 一覧で見慣れないステータス表記 | ⚠️で知らせる（画面の仕様変更の検知） |

## 6. Claude API の使い方

| 用途 | 出力 | モデル・effort（`config.toml` で変更可） |
|---|---|---|
| 承認者の返信の意図分類 | JSON `{intent, confidence, target_draft_id?}`（構造化出力） | `claude-sonnet-5-5` / effort `low` |
| 問い合わせの有無の判定 | JSON `{has_inquiry, reason}`（構造化出力） | `claude-sonnet-5-5` / effort `low` |
| 返信文案 | 文案の本文のみ | `claude-sonnet-5-5` / effort `medium`（2026-10-10 本人指定） |
| お礼文 | 1〜2文 | `claude-sonnet-5-5` / effort `low` |

- 安全上の判定で応答が拒否された場合に備え、サーバー側のフォールバック（`fallbacks: "default"`、beta `server-side-fallback-2026-07-01`）を有効にする。最終的に `stop_reason == "refusal"` なら文案を作らず、Slack に「文案を作れませんでした。手動で返信してください」と出す
- プロンプトに渡すのは、その予約に必要な情報だけ。電話番号・メールアドレスは渡さない
- 分類の確信度が低い場合は「判断できない」として人に確認する（F5）
- API の失敗は3回まで再試行し、だめなら⚠️で知らせる

## 8. 安全性・冪等性
- 外部への書き込み（承認、メッセージ送信、添付、レビュー投稿）の直前に必ず管理画面の現状を読み、実施済みなら飛ばして報告する
- 同じ予約への処理は、DB の比較更新と、プラットフォームごとのブラウザのロックで1つに絞る
- `DRY_RUN=true` のとき: Slack はテスト用チャンネル。管理画面は最後のボタンの直前まで進めてスクリーンショットを撮り、押さずに「(DRY_RUN) 送信したものとして扱う」で状態を進める
- 外部操作の前後でスクリーンショットを保存（30日で自動削除）
- 送る文面は承認された文字列と完全一致させる。送信後に画面上の文面を読み、承認文面と比べて一致しなければ⚠️

## 9. 運用・監視
- 停止、ログイン切れ、3回連続の失敗をチャンネルに⚠️（同じ警告は1時間に1回まで）
- デッドマンスイッチ（§1-2）
- `README.md`（セットアップ）、`docs/runbook.md`（障害対応）を用意
- 設定で変えられるもの: 暗証番号（資格情報）、定型文、承認者、リマインド間隔、ポーリング間隔、手数料率、モデル名、DRY_RUN

## 10. テスト
- 単体テスト: 管理画面のパーサ（保存した HTML。日跨ぎ、空欄、オプション、各ステータス）、意図分類のプロンプト（固定の例で）、状態遷移、リピート回数、収益計算、時間表記、宛名の名字の取り出し
- 結合テスト（DRY_RUN、テスト用チャンネル）: 依頼書 §10 の8シナリオ。新しい予約や新着メッセージは `barnull simulate …` で「ポーリングがこの予約・発言を見つけた」イベントとして投入し、管理画面は実在の予約で最後のボタン直前まで動かす
- **SM の「承認」ボタンは、承認待ちのリクエストが無いと画面で確認できない。** Phase 4 では、調査で取った DOM をもとにしたローカルの模擬ページで流れを確認し、実物は Phase 5 の最初のリクエストでご本人立ち会いのもと確定する

## 11. 実装・テスト時の進め方
- ログインが必要になった時は、私はパスワードを入力しない。`uv run barnull login sm|ib` をご本人がターミナルで実行する（画面付きで開き、保存済みの資格情報を使うか、手で入力する）
- 管理画面への書き込み（承認・送信・投稿）は Phase 5 までは押さない

## 12. 補足の設計判断

### 12-1. リピート回数とバックフィル
- 初回起動時（`barnull backfill`）に次の和集合で `guest_history` を作る
  - SM: 受信トレイ一覧の全ページ（予約ID・ステータス・日時・ゲスト名）
  - IB: 予約一覧（日付の絞り込みを掲載開始まで広げる。ゲストIDは `/partners/users/<ID>` から取れる）
- 照合キー: IB はゲストID。SM は管理画面の API 応答（`messages` の JSON）からユーザーIDが取れればそれを使い、取れなければ氏名の正規化一致にする
- 過去のホスト返信（`knowledge/past_replies/`）は両プラットフォームのスレッドから取り、ゲスト名は「◯◯さま」に置き換えて保存する

### 12-2. 返信文案の安全策（調査で実例があったもの）
- 直接取引の誘導（PayPay などプラットフォーム外での支払いの希望）には応じない文面にし、`【要確認】` を付ける
- 店内機器のパスワード（iPad 等）、キーボックス以外の暗証番号は書かない（`【要確認】`）
- 忘れ物・備品破損の申告は、事実確認が必要なので必ず `【要確認】` を付ける
- 文案の本文に `KEYBOX_CODE` の値が含まれていたら、送信を止めて⚠️（プロンプトには値を渡さないが、念のため）

### 12-3. ゲストのメッセージの Slack への転記
Slack の「ゲスト原文」には文面をそのまま引用するが、電話番号・メールアドレスらしき文字列は伏せ字にする。

## 13. 承認時の決定（2026-10-09）
1. 定型文の冒頭に「<名字>さま」を付ける
2. Gmail は使わない（管理画面のポーリングのみ）
3. SM の定型文はテキスト → PDF の順に送る
4. IB の承認制リクエストは自動承認せず、手動承認を依頼する → 2026-10-10 に変更: スタンプで承認して定型文を送る

## 14. 本番稼働後の点検による変更（2026-10-11）
本番開始直後の事故（SM の送信成否の誤判定、IB の確認ダイアログの自動キャンセル）を受けて、全体を点検し、次の方針に変えた。
1. **定型文（暗証番号）は、予約が確定しているときだけ送る。** SM は「予約完了」、IB は「予約確定」。承認制リクエストは承認後に状態が変わったことを確かめる。
   支払い待ち（SM「承認」、IB「予約未確定」）なら送らず、支払いの確認後に「💳 …スタンプで送ります」と知らせて、もう一度スタンプしてもらう
2. **「送信済み」の判定には暗証番号が必要。** 「キーボックスの暗証番号」の語だけの発言（「当日お送りします」など）は定型文とみなさない
3. **承認として扱うスタンプを限定する**（`approve_reactions`）。👀 などでは何もしない（2026-10-09 の「任意の絵文字」から変更）
4. **修正文の返信は、必ず確認のメッセージへのスタンプを経て送る**（スタッフ向けのメモや指示を誤って送らないため）。「送らない」と返信すれば文案を取り下げる
5. **送信の直前にスレッドを読み直す。** 同じ文面が送信済み、管理画面で手動返信済み、ゲストの新着がある、のどれかなら送らない。
   手動返信の判定から、システムが送った発言（定型文・PDF・送信済みの返信）は除く
6. **途中で止まった処理を回収する。** EXECUTING・COMPLETING・SENDING のまま残ったものは、起動時（と20分以上経ったもの）に ERROR にして再実行を依頼する。管理画面の操作には制限時間を設ける
7. **レビューの失敗は REVIEW_ERROR**（定型文の失敗の ERROR と分ける）。SM で退室時の記録が無ければ、自動で★5を付けず確認を求める。
   投稿済みか分からないときは投稿しない。承認者がレビューに触れた返信をしたら、はっきりしない内容でも自動投稿を止める
8. **停止中の Slack 操作の扱い。** 返信を先に、スタンプを後に処理する。同じ予約にスタンプと返信の両方があれば、順番が分からないのでスタンプは実行しない。
   問い合わせが予約リクエストに切り替わるときは、それまでのスタンプを「処理済み」として記録する
9. **秘密・個人情報。** Slack に出す本文・blocks・attachments はすべて伏せ字にし、ゲストの文字列は mrkdwn をエスケープする。
   失敗時のスクリーンショットは Slack に上げない（`upload_screenshots = false`）。ログの例外トレースバック、%エンコード・全角数字も伏せる。
   テスト用の画面データ（capture）は暗証番号を 0000 にする。自動で覚える回答は `knowledge/faq_learned.md`（手書きの FAQ と分け、上限つき）
10. **検知の取りこぼし対策。** 巡回は1件の失敗で止めない。IB の一覧が空ならエラー。SM 受信トレイの上位2行は毎回読み直す。
    一覧から外れた進行中の予約は3時間ごとに直接読み直す。巡回が25分以上成功しなければ警告する。Slack への投稿に失敗した通知・文案は出し直す
11. **メッセージの識別キー** は本文＋出現順（`h:`）に統一。以前の形式（`id:`・`at:`）とも照合する
12. **多重起動ロックは全モード共通**（`data/barnull.lock`）。`login`・`capture`・`backfill`・`doctor` も同じロックを取る
