## 2. 確認事項 (a)〜(i) への回答

**(a) SM で予約後にゲストがメッセージを送ったときの通知: あり**
- 件名は `【メッセージ】<ゲスト氏名>`。法人名があれば ` (<法人名>)` が付く。送信元は `info@spacemarket.com`（他の SM 通知は no-reply@）。185 通
- 本文（HTML）の構成: 見出し「メッセージが届きました」、`<氏名>さんから`（法人名付きの場合は `<氏名> (<法人名>)さんから`）、メッセージ本文、「返信する」ボタン、「予約リクエスト内容」表（予約ID・お名前・法人・団体名・スペース名・住所・利用期間・人数・利用目的・利用用途の詳細）。料金欄はない
- メッセージ本文は全文が載る（改行は `<br>`）。添付だけのメッセージは本文が「ファイルが添付されました」になり、ファイル自体は載らない
- 予約前の問い合わせ段階でも同じ件名で届く。その場合は「利用期間」が空欄
- 「利用期間」は送信時点の最新値。延長後は延長後の終了時刻になる

**(b) SM のキャンセル通知の件名**
- `キャンセルが完了しました。払戻金額を確認ください`（3 通、2 件分）
- 本文の見出しは「払い戻しが完了しました」。文面は「ゲストによって予約リクエストがキャンセルされました。設定されたキャンセルポリシーに従い、自動で払い戻しを行いました。」に続き、「払い戻し料金の明細」と予約の詳細表（料金欄あり）
- 観測した 2 件はどちらも払い戻し額が合計額と同じだった（キャンセル料なし）。キャンセル料が発生したケースは未観測
- ホスト側からのキャンセル通知は該当メールなし（全期間 553 通中）

**(e) SM メールに含まれる識別子**
- 予約ID（7 桁）は、表の「予約ID」行にある。対象は予約リクエスト、予約完了、メッセージ、延長、退室時状態、キャンセル、変更リクエスト、未返信リクエスト、予約リクエストへの変更、お問い合わせ。お問い合わせの段階で、すでに予約IDが振られている
- 次の種類は予約IDが URL の中にしかない:
  - 変更承諾: 表には予約IDと金額だけがある
  - コロンなしのリマインド
  - レビュー依頼のリマインド（`/inbox/<予約ID>/review`）
  - レビューを書きましょう
  - 未対応の問い合わせ
- メッセージ期限切れには予約IDがない（スペースの公開 URL だけ）
- ゲスト名は表の「お名前」行にある（メッセージは件名と「〜さんから」にもある）。ゲスト名がない種類は次のとおり:
  - 変更承諾
  - コロンなしのリマインド

- ダッシュボード URL の形は `https://dashboard.spacemarket.com/<ホスト識別子>/inbox/<予約ID>`。末尾に `#message`（メッセージ・退室時状態）や `/review`（レビュー）が付く場合がある。`<ホスト識別子>` は数値のホストID（アカウント系メールに出る 5 桁の数字）ではなく、英数字と `_` からなる 16 文字のスラッグ（例 `of4x48usi2_b8kyu`）

  - 予約ID は 10 桁で、予約・リクエストの件名と本文の両方にある
  - ゲスト名は `お客様氏名: ○○様` の形で載る。フリガナは確定、リクエスト、承認、変更確定、前日リマインドにはあるが、キャンセルとレビュー系にはない
  - ゲストのユーザーIDは `【要対応】予約リクエスト` に限り、`https://www.instabase.jp/partners/users/<10 桁>/inbox` の形で載る（フィクスチャでは `5000000001` に置換）

**(f) IB メッセージ通知の `/partners/inbox/{スレッドID}` と予約IDの関係**
- 本文に予約IDはない。メッセージ本文もない
- 本文にあるのは、ゲスト名（`「○○」様よりメッセージが届きました。`）、対象スペース、`https://www.instabase.jp/partners/inbox/<7 桁>` だけ

- ゲスト名はイニシャルや空白入りの表記のこともある（例 `「N T」`。Gmail の snippet では `NT` と表示される）

- IB の支払明細書メールに載るのは「売上の振込日」と明細一覧の URL だけで、金額はない

**(h) 退室時状態メールの「状態」の値**
- 全 7 通を確認した
  - 「問題なく退室しました」が 6 通
  - 「気になる点があります」が 1 通
- 「気になる点があります」の場合は、状態表に次の 2 行が加わる
  - 「種類」行: 観測した値は「備品・設備に不備があります」
  - 「詳細」行: ゲストの自由記述。複数段落の `<p>` と `<br>`。内容はグラス破損の申告と、退出写真がないことの説明
- 添付写真はメールに含まれない。リンク先（`inbox/<予約ID>#message`）で確認する

**(i) 予約日時表記のバリエーション**

SM:
- 形式は `YYYY/M/D(曜) H:MM〜H:MM`
  - 月・日・時はゼロ埋めしない（例 `2026/9/30(水) 0:00〜4:30`、`2026/11/23(月) 9:45〜15:45`）
  - 波線は U+301C（〜）
- 日をまたぐ場合は、終了側にも日付が付く
  - 例 `2026/10/8(木) 21:00〜2026/10/9(金) 0:00`、`2026/8/28(金) 21:00〜2026/8/29(土) 2:00`、`2026/5/15(金) 21:00〜2026/5/16(土) 2:00`
  - 終了が 0:00 ちょうどでも翌日の日付になる
- 0 時ちょうどに始まる場合は、開始日が翌日になり、終了側に日付は付かない（例 `2026/9/30(水) 0:00〜4:30`）
- 予約リクエストの冒頭行とリマインドでは `利用期間：…`（全角コロン）
- お問い合わせの「利用希望日時」は未指定なら `-`。問い合わせ段階のメッセージでは「利用期間」が空欄になる
- レビュー期限は `2026年10月7日 14:00` や `2026年10月14日 4:30`（時のゼロ埋めなし）、または `2026年10月23日`（時刻なし）

IB:
- 形式は `YYYY年MM月DD日(曜) HH時MM分〜HH時MM分`（すべてゼロ埋め）
- 終了側には日付が付かない
- 準備日時・清掃日時が別行で付く。通常は前後 30 分。深夜帯の例では前後 60 分だった
- 日をまたぐ例:
  - 利用日時 `2026年05月31日(日) 00時00分〜05時00分`
  - 準備日時 `2026年05月30日(土) 23時00分〜00時00分`（準備のほうが前日にかかる）
- 開始が 21 時台などで翌日に終わる IB 予約は観測できなかった。その場合も終了側は時刻だけと推測されるので、「終了 ≤ 開始なら翌日」と解釈する実装を勧める（未確認）
- レビュー依頼は `2026年10月01日(木) 利用のご予約で`

## 3. 種類ごとの取得項目とパース上の注意

### SM 共通
- **text/plain パートがない（HTML のみ）**。`get_message(FULL_CONTENT)` では `htmlBody` だけが返り、`plaintextBody` はない
- `PLAIN_TEXT` を指定すると、Gmail コネクタが HTML を Markdown の表に近い形（`| ラベル | 値 |` と `|---|---|` の繰り返し）に変換したものが返る。この形も参考としてフィクスチャに含めた（下の「フィクスチャの作り方」参照）
- コネクタが返す HTML の改行は `\r\r\n`。レビュー依頼のリマインドだけ `\n`
- 詳細表は `<tr><th>ラベル</th><td>値</td></tr>` の形。th と td は `display:block` で縦に並ぶ。ラベルは次のとおり:
  - 予約ID
  - お名前
  - 法人・団体名（なければ `-`）
  - スペース名（部屋名。時期によって変わり、全角空白を含む）
  - 住所
  - 利用期間
  - 人数（例 `〜15人`）
  - 利用目的
  - 利用用途の詳細
  - 利用料金
- 値の前後に改行と空白が入る（特に利用期間と人数）。strip が必要
- 「利用用途の詳細」は `<p>…</p>` で囲まれ、改行は `<br>`。空なら `<p></p>`
- 利用料金は入れ子の表で、行は「プラン料金」「消費税」「合計」の 3 つ
  - プラン料金の値は `夜プラン（￥30,000）` の形（全角括弧、全角円記号 U+FFE5、カンマ区切り）
  - 消費税と合計は `￥3,000` の形
  - Gmail の snippet ではカンマが落ちて `￥5000` になる
- 人数の記号は U+301C（〜）
- ボタンのリンクは `dashboard.spacemarket.com/<スラッグ>/inbox/<予約ID>` の形
- 件名末尾の会場名と表のスペース名はどちらも時期によって変わる。判定は件名の接頭辞で行う

### SM 種類ごとの注意
- **予約リクエスト**: 冒頭に `利用期間：…`、続けて詳細表と料金表。ボタンは「リクエストに返答」
- **予約完了**: 詳細表と料金表。本文の「予約リクエストの変更は、スペース利用終了日の翌月1日／翌月2日まで」は、メールによって 1 日と 2 日が混在している
- **メッセージ**: 上記 (a) のとおり。料金表はない。件名から氏名を取る場合は ` (法人名)` を分離する
- **お問い合わせ**: 表の形式が異なる
  - th の style が違い、ラベルは「お名前、法人・団体名、住所、予約ID、会場名、スペース名、利用希望日時、利用目的、利用区分（個人利用／法人利用）、人数、予算、お問い合わせ事項」
  - 本文は「最新のメッセージから14日が経過したメッセージは、期限切れとなり自動的に終了します。」。2025-12 の問い合わせでは「3日」だった
- **退室時状態**: 状態表（状態、種類、詳細）と予約詳細表（料金表なし）の 2 つの表がある。フッターは他と違う（app ad 版）
- **キャンセル**: 「払い戻し料金の明細」の HTML が壊れている（`<tbody>` の直下に `<td>`、`<table>` の直下に `<p>`）。lxml や html5lib は構造を補正するので、払い戻し額はラベル文字列で探して取り出すのが安全
- **変更リクエスト**: 変更後の内容だけが載り、変更前は載らない。差分を出すには保存済みの予約と比べる必要がある
- **変更承諾**: 予約IDと料金表だけが載る
- **延長**: 延長後の利用期間と料金が載る。延長のたびに 1 通届く（15 分刻みの延長で 5 通届いた例あり）
- **コロンなしの「予約リクエストが届きました」**: カード形式。利用期間、スペース名、利用目的・利用区分・人数のタグ、ゲストのメッセージがあり、予約IDは URL にしかない。ゲスト名はない
- **レビュー依頼のリマインド**: 予約IDは URL の `/inbox/<id>/review` にある。提出期限の日時も載る

### IB 共通
- text/plain パートがある（HTML もあるが、リンクは `link.instabase.jp/ls/click?upn=…` の追跡リダイレクトに置き換わっている）。**plain を使うのを勧める**。フィクスチャは plain のみで、html_body は null
- 宛先は host@example.com で、CC にもう 1 人の社内アドレスが入る（2026-06-05 頃以降の業務通知）
- 冒頭は `株式会社○○様`（フィクスチャでは `株式会社ホスト様`）
- 予約詳細ブロックは `━━━━━━━━━━━━━━━━━━━━`（U+2501 が 20 個）で囲まれ、各行は `ラベル: 値` の形。ラベルは次のとおり:
  - 予約スペース（リマインドとキャンセルでは「スペース」）
  - お客様氏名（末尾に `様`）
  - フリガナ
  - 予約ID
  - 予約詳細（`https://www.instabase.jp/partners/bookings/<予約ID>`）
  - 利用日時
  - 準備日時
  - 清掃日時
  - 料金プラン
  - 利用料金（`18,150円 (税込)`）
  - 利用人数（`7名`）
  - 利用用途（`大分類 - 小分類`）
  - 用途詳細
  - オプション（`・ゴミ処理 x1個` が複数行並び、`※ オプションの料金は…` 行で終わる。オプションがなければブロックごとない）
- 区切り文字の揺れ:
  - 未対応リクエストのキャンセルは `スペース:Bar null` `お客様氏名:○○様` のようにコロンの後に空白がない
  - レビュー依頼は `予約ID：…` `お客様氏名：…様` と全角コロン
  - 正規表現は `\s*[:：]\s*` のように両方を許すこと

- レビュー依頼にはレビュー投稿 URL `…/bookings/<予約ID>/user_reviews/new` がある
- 受け取ったレビューの通知には `…/partners/reviews/<10 桁>` がある。このIDは予約IDとは別物（未確認）
- 用途詳細は 1 行。ゲストが入力した改行が保持されるかは未確認

## 5. リスク・未確認事項

1. **Gmail コネクタの癖**
   - search_threads の一覧は 1 スレッドあたり最大 5 通で、それを超える分は `messageCount` にしか現れない。新着を取りこぼさないよう、get_thread でスレッドを全件取得するか、時刻で絞った検索を使う
   - ツールの出力が一定サイズ（約 25k トークン）を超えると、インラインではなくファイルに退避される
2. **Gmail のスレッド分けは件名単位**。別のゲストのメールが同じスレッドにまとまることがある（IB のメッセージ通知で実例あり）。Gmail の threadId を予約やゲストの単位として使ってはいけない
3. **件名の前方一致による誤判定**: `予約リクエストが届きました`（リマインド）と `予約リクエストが届きました：…`（新規）、`【予約内容の変更リクエスト】` と `【予約内容の変更リクエスト：承諾】` は、区切りまで含めて完全一致で判定する
4. **状態遷移の一部はメールが来ない**: SM の否認、リクエスト期限切れ、ホスト側キャンセル、変更の却下を知らせるメールは観測できなかった。IB も同様。メールだけで予約の最終状態を確定できないので、ダッシュボードとの突き合わせが必要
5. **IB のメッセージ通知には本文も予約IDもない**。自動応答を作るには IB 管理画面の受信箱を読む必要がある（別途ブラウザ調査）
6. **重複通知**: SM のキャンセルが 1 秒差で 2 通（同じ予約）、SM の延長が都度 1 通、レビューのリマインドが同じ予約で複数回届く。処理は予約IDと種類で冪等にする
7. **ゲストのメッセージに含まれる注意点**（自動応答の安全策が要る）:
   - ホストの名字での呼びかけ
   - PayPay での直接支払いの希望。SM は規約で直接取引を禁止している
   - iPad のパスワードを尋ねる質問
   - 退室後の忘れ物の問い合わせ、備品破損の申告
   - なお、キーボックス等の暗証番号らしき 4 桁の数字は、取得したメール本文には含まれていなかった
8. **未確認事項**:
   - IB で開始が深夜より前の日またぎ予約の表記
   - SM でキャンセル料が発生したキャンセルの表記
   - SM で否認・期限切れの際にゲスト側で何が起きるか
   - IB の用途詳細に改行が入った場合の表記
   - IB 受け取りレビュー通知の ID の意味
   - SM の会場名・スペース名が今後も変わること（キャンペーン名が入るため）
9. **個人情報**: CC に別の社員アドレスが入っている。SM のメッセージは全文がメールに載るので、ログや通知（Slack 等）に転記するときはマスクが必要
10. **時刻**: Gmail の `date` は UTC、本文の日時は JST。境界の判定（前日リマインドや 0:00 開始など）では変換を誤りやすい
