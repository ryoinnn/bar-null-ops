# 設計: 勤怠・スタッフ管理・給与（実装計画）

- 状態: **案**（2026-11-14）。本人の了承後に実装する
- 改訂（2026-11-26 本人の指示）: **勤怠はすべて桝本の承認を待つ**（期限内も）。承認されるまでは記録・Asana・給与（ポータル）に載せない。
  承認待ちのリマインドは、依頼のスレッドで毎日1回。前の版は [old/labor_design.md/](old/labor_design.md/)
- 要件: [labor_requirements.md](labor_requirements.md)。作法は売上の伝票と同じ（事実を保存 → 状態を計算、保存と反映を分ける、やり直しても同じ結果）

## 1. 全体
```
LINE「Bar null」 @null ─▶ sales-webhook（変更なし）─▶ Cloud Tasks ─▶ sales-worker /tasks/process-event
   extract.py が種類を判定: slip_content（伝票。プロモーターフラグを追加）／ attendance（勤怠。新）／ …
   ├ 勤怠 → attendance.py: 本人の特定 → 承認待ち（すべて。期限切れ・未来の日付・訂正は目印）→ 承認で記録
   └ 伝票 → 既存の処理。保存のたびに「本人の売上」が変わったかを見て、勤怠の売上と給与を直す
/jobs/reconcile（30分ごと。既存）に足すステップ:
   staff_sync（Asana の台帳を読む）→ attendance_approvals（Slack の ✅/❌・毎日のリマインド）→ attendance_overrides（Asana の手動上書き）
   → attendance_resync（反映のやり直し）→ payroll（第1水曜 17:00 の計算、10日 9:00 の確定）
```
新しい Cloud Run・Cloud Scheduler・Secret は作らない。

### 本番に出す前の試し方
`[labor] dry_run = true`（勤怠だけの切替。売上は今の本番のまま）。true のあいだ、勤怠・台帳・給与は **テスト用の Asana プロジェクトと #test_barnull-sales** に書く。
LINE の本番グループで実際に打って確かめ、本人の確認後に false にする。

## 2. データ（Firestore が正本。Asana は台帳）

| コレクション | 内容 |
|---|---|
| `staff/{スタッフID}` | 台帳の写し: 本名、LINE名、区分、入社日、時給の履歴 `[{from, wage}]`、バック率、LINE ID の一覧、Asana の gid |
| `attendance/{記録ID}` | 勤怠1件: スタッフID、LINE ID、営業日、開始・終了（ISO）、時間、本人の売上、時給の額、状態、訂正の履歴、Slack・Asana の ID、sync_pending、当てた入力のいちばん新しい送信時刻（applied_sent_at。前の版の記録には無く、承認で当てた入力は依頼の送信時刻、すぐ記録した入力は記録した時刻で代える）、保存の後の反映がまだか（after_save） |
| `attendance_pending/{イベントID}` | 承認の依頼（すべての勤怠）: 解析結果、送信時刻、quoteToken、記録ID、目印（訂正・期限切れ・未来の日付）、訂正前の記録、Slack の ts、状態（waiting／approved／rejected／superseded＝同じ日の新しい入力で取り下げ／closed＝給与の確定で締め切り）、最後にリマインドした日、Slack の後始末がまだか（finish_pending）、LINE の承認の連絡がまだか（announce_pending）とその組の retry_key（announce_key） |
| `payroll/{YYYY-MM}_{スタッフID}` | 給与1件: 勤務日数、時間、時給の分、売上、バック、調整額、給与、状態（計算済み／確定）、再計算の履歴、Asana の gid |
| `payroll_runs/{YYYY-MM}` | 月の計算・確定をしたか（二重に動かさない） |

- スタッフID: 台帳の Asana タスクの gid（台帳に無い人は `line-{LINE ID の先頭8文字}` で仮に作る）
- 記録ID: `W-{営業日 YYYYMMDD}-{スタッフID}`。同じ人・同じ日は同じ ID なので、二重にできない（2回目は上書き）
- 時給・バック率・給与は Firestore と非公開の Asana にだけ置く。git・ログ・Slack には出さない

## 3. 勤怠の処理（`attendance.py`）
1. 解析（`extract.py` に `attendance` を追加）: 日付（月・日）、勤務開始・勤務終了（`HH:MM`、`25:00` 可）。時刻の日付への当てはめは Python で行う（§要件 2-1）
2. 検証: 時間が 0 より大きく 15 時間以下。外れたら「読み取れない勤怠」として Slack に出す（スタンプなし）
3. 本人の特定: LINE ID → 台帳。無ければ表示名を台帳の LINE名と照合（空白・敬称を除く）し、合えば LINE ID を台帳に記録。
   どちらも無ければ台帳に仮の人を作り（LINE名 ＝ 表示名、ほかは空）、Slack で「台帳に足してください」
4. 給与が確定した月なら、記録せず Slack で知らせ、LINE に「確定済みのため LINE からは直せない」と返信する
5. **承認待ち（§5）**。すべての入力が対象。`送信時刻 > 営業日+2日 9:00` は「期限切れ」、`勤務開始 > 送信時刻` は「未来の日付」、
   同じ記録 ID がすでにあれば「訂正」の目印を依頼に付ける。承認されるまでは 6〜8 のどれもしない
6. 承認されたら記録: `attendance/{記録ID}` を保存 → その日の本人の売上・時給の額を計算 → Slack・Asana を作成／更新 → LINE で知らせる
7. 訂正の承認: 変更前後を記録の Slack スレッドに出す。同じイベントを二度は当てない（履歴にイベント ID）
8. 給与が「計算済み」の月なら、その人の給与を計算し直す（§6）

### Slack（`#null_staff-management`）
- 1件ごとに親メッセージ: `本名｜11/23（日）21:00〜03:00　6.0h｜今月の平均 5.4h（12日・65.0h）`。訂正はスレッドと親の書き換え
- 新しい記録は、承認依頼の投稿をそのまま親メッセージに書き換える（1件の勤怠でチャンネルの投稿は1つ。依頼と承認のやり取りはそのスレッドに残る）
- 親メッセージが Slack で消されていたら（message_not_found）、次に記録が変わったとき（訂正の承認・売上の変化など）に出し直す
- 承認の依頼、台帳に無い人、読み取れない勤怠、給与の計算・確定・再計算、確定後の売上の変化もここに出す（額は出さない。「Asana の給与を見てください」とリンクだけ）

## 4. 伝票のプロモーターフラグ
- `extract.py` の伝票の項目に `promoter_name`（無ければ空）を足し、プロンプトに「プロモーターフラグ：」の行を説明する
- `Slip.promoter_name` を足す。Slack の親メッセージに `プロモーター：〇〇`、Asana に「プロモーター」（テキスト）、`restore-from-asana` で戻す
- 訂正（`correction`）でプロモーターも直せるようにする
- 本人の売上の帰属（§要件 4-2）: プロモーター名があれば台帳の LINE名（無ければ本名）で照合したその人、無ければ送った人の LINE ID

## 5. 承認（すべての勤怠。2026-11-26 から）
1. 受け付け（LINE のイベントの処理）: `attendance_pending/{イベントID}` を保存 → Slack に桝本をメンションして依頼を投稿 → LINE に引用付きで返信（reply。無料）
   - 依頼の見出し: `【勤怠の承認依頼（訂正・期限切れ）】本名｜11/23（月）　21:30〜03:00　5.5h`。訂正なら「今の記録」、送信時刻と期限、原文を添える
   - 同じ人・同じ日の承認待ちがあれば、**後の入力を残し**、古い依頼は「取り下げ」（投稿の見出しを【取り下げ】に書き換え、スレッドに一言）
   - 前の承認待ちと同じ内容なら依頼を増やさない（「同じ内容で承認待ちです」と返信）。記録と同じ内容なら依頼を出さない（「記録済みです」と返信。承認待ちの訂正があれば取り下げる）。
     どちらも、その入力の時刻を残す（依頼の latest_sent_at・記録の applied_sent_at）。遅れて届いたもっと古い入力を、後から当てないため。
     記録より古い承認待ちと同じ内容のときは、新しい依頼を出す（古い依頼は取り下げる）
   - 遅れて届いた古い入力（同じ日にもっと後に送られた入力がある。承認待ち・記録済み・却下・取り下げのどれでも）は使わない（LINE に「後の入力を使う」と返信）
   - Slack に出せなければ、LINE には返信し、30分ごとの `attendance_approvals` が出し直す
   - 途中で落ちて Cloud Tasks がやり直したときも、古い依頼の取り下げ・依頼・返信の続きから行う（依頼と返信は一度だけ）
2. 30分ごとの `attendance_approvals`（承認待ちを送信の古い順に。1件ずつ読み直し、まだ承認待ちのものだけ扱う）:
   - 給与が確定した月の依頼 → 「締め切り」（記録しない。スレッドで桝本に「Asana の調整額で直してください」。Slack に出せていなかった依頼は、チャンネルに同じ知らせを出す）
   - すでに記録に当てた依頼（承認して記録した後、状態を保存する前に落ちたもの）→ 保存の後の反映（Slack・Asana・訂正のスレッド・給与の計算し直し。
     記録の after_save）の続きをしてから、リアクションに関係なく承認済みにする（記録は二重に当てない）。こうした依頼は、同じ日の承認待ちとしては数えない
   - 前の版の依頼（record_id なし）は、最初の回に一度だけ、前の版で決まった同じ日の依頼（却下など）も見て、後に送られた入力があれば取り下げる。無ければ record_id を付ける
   - 同じ日のもっと新しい入力（承認待ち・記録済み）がある依頼 → 「取り下げ」。同じ日のもっと古い承認待ちも取り下げる（**承認待ちは、いつも最新の入力の1つだけ**。前の版が残した重複もここで片付く）
   - リアクション（`reactions.get`）。**桝本（alert_mention）が付けたものだけ**数える。依頼の投稿が Slack で消されていたら（message_not_found）、依頼を出し直す
   - ✅（`white_check_mark`・`heavy_check_mark`・`o`）→ 記録（§3 の 6〜8）。新しい記録は依頼の投稿を親メッセージにする。訂正は依頼の見出しを【承認済み】にする。
     LINE に元のメッセージを引用して「承認され、記録しました」とプッシュ送信（同じ回の承認は、グループごとに1回の送信へ5件までまとめる。
     承認の保存と一緒に announce_pending を立て、送れたら下ろす。送る組と retry_key は送る前に保存し、落ちた後も同じ組・同じ key で送る（二重に届かない）。
     送れなければ Slack のスレッドに残して諦める。`approval_line_notice = false` で止められる（月の無料枠が足りないとき。受け付けの返信の「お知らせします」も消える））
   - ❌（`x`・`negative_squared_cross_mark`）→ 記録しない。見出しを【却下】にし、スレッドに「却下しました」。LINE には知らせない（要件 §2-3）
   - どちらも無い → **毎日1回リマインド**（下の 3）
   - 決めた依頼（承認・却下・取り下げ・締め切り）は、状態と一緒に Slack の後始末（見出しの書き換え・スレッドの一言）を finish_pending として保存し、
     済んだら下ろす。後始末の前に落ちた・Slack が失敗したものは、次の回からやり直す（48回＝約1日で諦める）
   - 記録の保存の後の反映（訂正のスレッド・給与の計算し直し）は after_save に残し、済んだものから下ろす。失敗したものは 30分ごとの
     `attendance_resync` がやり直す（給与の確定より前の `payroll` のステップより先に動く）
3. リマインド: 依頼した日の翌日から、毎日 `approval_remind_time`（10:00）以降の最初の回に、依頼のスレッドへ桝本をメンションして返信する
   （「スレッドの一番上の依頼に ✅ か ❌ を」。リアクションは依頼の投稿のものだけ数える。記録があれば「今の記録」も添える）。
   同じ日に二度は送らない（`reminded_on`）。決まった（承認・却下・取り下げ・締め切り）依頼には送らない。前の版の依頼（`reminded` のみ）にも同じく送る。
   前月の依頼には、給与の計算日の前なら「計算します。承認されていない勤怠は給与に入りません」、計算の後なら「確定までに承認すれば給与に入ります」を添える（訂正なら「承認されるまで前の記録のまま給与に入ります」「承認すれば計算し直します」）
4. 承認されていない勤怠は給与に入らない（訂正は前の記録のまま入る）。第1水曜 17:00 の計算の知らせに「承認待ちの勤怠が N 件」「承認待ちの訂正が M 件」と出す。確定（10日 9:00）までに承認すれば、その人の給与を計算し直す
5. 読み取りの数: 承認待ちは「状態 = waiting」の一覧（いつも少ない）から探し、決まった過去の依頼は読まない（`attendance_pending` は消さないので増え続けるため。
   Firestore の読み取りの無料枠は1日5万。承認待ち10件で1回 約40件の読み取り）

## 6. 給与（`payroll.py`）
- 計算: `給与 ＝ Σ(勤務時間 × その日の時給) ＋ 本人の前月の売上 × バック率 ＋ 調整額`（円未満切り捨て）。時給は勤務日に有効な履歴の額
- `payroll` ステップ（30分ごと）: 
  - 今が「その月の第1水曜 17:00」を過ぎ、`payroll_runs/{前月}` が未計算 → 管理者を除く全員を計算（状態: 計算済み）→ Asana に作成、Slack に「計算しました」
  - 今が「10日 9:00」を過ぎ、計算済み → 確定（Asana の状態も確定）
- 計算し直し（定期的な見回りはしない。保存のときに動く）:
  - 伝票の保存（`slip_ops.save`・起票）で、伝票の「帰属先・営業日・金額・取消」のどれかが変わったら、変わる前後の人と月を調べる
  - 勤怠の承認（新規・訂正）・手動上書きのとき、その人と月
  - その月が計算済み → その人の給与を計算し直して Asana を更新し、Slack に「再計算しました」
  - その月が確定 → 計算し直さず、Slack に「確定後に前月の売上が変わりました（〇〇さん）」
- 確定後の変更: 管理者が Asana の給与タスクの「調整額」「調整の理由」を入れる → 30分以内に取り込み、給与に足す

## 7. Asana（新しいプロジェクト。本番とテストの2つずつ、非公開・管理者2人だけ）

| プロジェクト | 1タスク | 主な項目 |
|---|---|---|
| Bar null 勤怠 | 1人 × 1営業日 | スタッフ名、稼働日、稼働時間（h）、勤務開始、勤務終了、売上（本人）、時給の額、状態（記録済み／対象外）、記録ID、スタッフID、店舗、Slackスレッド、手動上書き（なし／時間を反映／対象外） |
| Bar null スタッフ台帳 | 1人 | 本名、LINE名、区分（スタッフ／プロモーター／管理者）、入社日、時給、時給の適用開始日、バック率、スタッフID |
| Bar null 給与 | 1人 × 1か月 | 対象月、区分、勤務日数、勤務時間、売上、時給の分、バック、調整額、調整の理由、給与、状態（計算済み／確定）、スタッフID |

- 勤怠の「時給の額」は、画面で「その日時点のコスト」を正しく出すため（時給を途中で変えても、過去の日の額が変わらない）
- 台帳は管理者が Asana で直す（画面から書き込めるようになれば画面から）。30分ごとの `staff_sync` が変更を読み、時給が変わったら履歴に足す
- 勤怠の手動上書き: 管理者が「勤務開始・勤務終了」を書き換えて「時間を反映」、または「対象外」→ 30分以内に取り込む
- ID は `asana_ids.json` の `labor` に保存（`uv run barnull-sales asana-setup-labor --env test|prod`）。カスタムフィールドはワークスペース共通

## 11. 進める順番
1. 伝票のプロモーターフラグ（A が待っている。小さい）→ テスト → コミット → push → A に知らせる
2. 勤怠の受け付け・台帳・Slack・Asana・承認 → `[labor] dry_run = true` で本番の LINE から試す
