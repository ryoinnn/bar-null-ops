```text
Bar null の売上管理自動化（sales/）を、利益ベースで見られるように拡張している。あなたはそのうち「仕入（コスト）管理」を担当する。

目標: 酒屋の Web アプリ（注文・請求の画面）を Claude がブラウザで操作して、毎週、定期実行で仕入の情報を取りに行き、Asana に記録する。
記録は売上レポート（Artifact）の利益セクションで、原価・変動費として使う。

最初に、次の順で読んで、現行のシステムを理解してから始めること（コードも必要な範囲で読む）。
1. sales/docs/profit/README.md（全体の分担）
2. sales/docs/profit/handoff.md（現行の仕様・守るルール・作法）
3. sales/docs/profit/contract.md（レポートとの約束。あなたの担当は §3。確定したら最終版に書き換える）
4. sales/docs/design.md、sales/docs/decisions.md、sales/src/barnull_sales/asana.py、cli.py（Asana のプロジェクトを作る仕組み）
5. 参考にできる前例（ブラウザを定期実行で操作する仕組み）:
   - リポジトリ直下の src/barnull/（予約対応。Playwright の決まった手順で管理画面を巡回し、ログインは本人が手元で行う）と docs/design.md
   - C:\Users\ryoui\Documents\consul-autoapply（Claude in Chrome で巡回する定時チェック。procedures/、rules/safety.md、scheduler/ にある。Windows タスクスケジューラ → claude --chrome）

進め方:
- 最初に、本人への確認事項を1回にまとめて聞く。決められるものは推奨を添えて自分で決めて進める。
  聞くこと（例）: 酒屋のサイトの名前・URL とログイン方法（二段階認証の有無）／取れる情報（注文履歴・納品書・請求書、明細の有無）／
  仕入の計上日（納品日 or 請求日）と税込・税抜／区分（酒類・食材・消耗品）の分け方／仕入先は酒屋だけか／実行する曜日と時刻／福岡 Node の仕入も扱うか。
- 先にサイトの利用規約を読み、自動操作・ボット・スクレイピングの禁止条項がないか確認する。禁止されていたら操作せず、本人に報告して別の取得方法（メール・CSV・請求書の取り込み）を相談する。
- ログインは本人が行う。パスワード・認証コードは Claude が入力しない。ログイン状態が切れていたら、その回は止めて本人に知らせる。
- 実行の場所は、無料枠と課金の自動停止に注意して選ぶ（Cloud Scheduler はすでに無料枠の3本を使い切っている）。
  推奨の案: 本人の PC で、Windows タスクスケジューラ → Claude Code（または既存の Playwright 方式）で毎週実行し、
  取得結果を Asana の仕入プロジェクトに書く。クラウドに新しい定期実行を足す案は、費用を確認してから本人に相談する。
- 取得は読み取りだけ。注文・支払・設定変更などの操作はしない。取り込めた件数・読めなかった項目を、実行のたびに Slack（またはレポートファイル）に短く知らせる。
- 同じ注文を二重に記録しない（注文番号で判定する）。値引き・返品は元の記録を直す。
- 設計案を短くまとめて本人に見せ、了承を得てから実装する。まずテスト用の Asana プロジェクトで動かし、本人が確認してから本番にする。
- 酒屋の画面・価格・取引先の情報は、このリポジトリの git に入れない（サンプルは sales/samples/ のように git に入れない場所に置く）。
- レポートの画面（sales/report/weekly_report.html）は別セッション（A）が担当する。あなたは直さない。
  Asana の項目・記録 ID・状態が確定したら contract.md §3 を最終版にして、本人に知らせる。
- 守るルール（handoff.md §4）: 日本語、パスワード等を入力しない、組織ポリシーや権限の変更は本人が実行、コミットしてよいが push は本人に依頼する。

ゴールの完成条件: 毎週の定期実行で、酒屋の仕入が営業日・区分・金額つきで Asana の仕入プロジェクトに冪等に記録され、失敗したら本人に分かり、
運用手順（docs/runbook.md に節を追加）が揃い、contract.md の §3 が実装と一致していること。
```
