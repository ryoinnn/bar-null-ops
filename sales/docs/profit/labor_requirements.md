## 1. 用語

| 用語 | 意味 |
|---|---|
| 勤怠サイクル | **21:00〜翌9:00** を1サイクルとする。日付はサイクルが始まる日 |
| 営業日（勤怠） | スタッフが「日付：」に書いた日 ＝ その勤務のサイクルの開始日 |
| 営業日（売上） | 既存の 6:00〜翌6:00。伝票の「日付：」で決まる。勤怠と同じ日付で突き合わせる |
| スタッフ | 時給が発生する人。バック率も設定できる |
| プロモーター | 個人の営業代理店。バック率だけが発生する（時給なし） |
| 管理者 | 勤怠を登録しない人（岡本颯真、桝本崚允）。スタッフの集計から除く |
| LINE名 | スタッフ台帳に登録する LINE の表示名。LINE の送信者とプロモーターフラグの名前は、これで本人に結び付ける |
| 本名 | 画面と給与の表示に使う名前 |
| バック | 本人の月の売上 × バック率 |
| 給与 | 時給 × 勤務時間の合計 ＋ バック（§5） |
| その日時点 | 月初からその日までの累計 |

契約の形: スタッフ・プロモーターとも **業務委託**（2026-11-14 本人）。深夜・時間外の割増と休憩の義務は扱わない。

## 2. 勤怠の入力（LINE）

### 2-1. 打ち方
同じ LINE グループ「Bar null」で、Bot へのメンションをきっかけに受け付ける（伝票と同じ仕組み）。

```
@null
日付：11/23
勤務開始：21:00
勤務終了：3:00
```

- 1通 ＝ 1人の1営業日の勤務。勤務が終わってから、開始と終了を1通で送る（「勤務中」の状態は持たない）
- 休憩は無い（考慮しない）。勤務時間 ＝ 終了 − 開始
- 時刻の読み方: 9:00〜23:59 は「日付」の日。0:00〜8:59 と「25:00」のような書き方は翌日。終了が開始より前なら翌日
- 解析は既存の Claude Haiku（`extract.py` に種類 `attendance` を足す）。自由な書き方も読み取る
- 送った人は、LINE の個人 ID と表示名で本人に結び付ける（§3-3）

### 2-2. 受け付けたとき
- 正しく読み取れたら、**すぐには記録せず承認待ちにする**（期限内・期限切れ・未来の日付・訂正のどれも）。
  元のメッセージを引用して「受け付けました。管理者が承認したら記録し、お知らせします」と返信する（返信は無料。「OK」スタンプの代わり）
- 読み取れなければ返信しない。Slack に「読み取れない勤怠」を出す

### 2-3. 承認（すべての勤怠。2026-11-26 本人）
- **いかなる場合も、勤怠の入力は管理者（桝本）の承認を求める。承認されたものだけを、記録・Asana・給与・ポータルに反映する**
- 期限: **営業日 D の勤務は、D+2 日の 9:00 まで**（例: 11/23 の勤務 → 11/25 9:00 まで）。過ぎた入力は承認の依頼に「期限切れ」と出す（承認すれば記録できる）。
  未来の日付の入力も「未来の日付」と出す
  1. LINE: 元のメッセージを引用して「承認待ち」と返信する（期限切れ・未来の日付なら、そのことも書く）
  2. Slack（スタッフ管理のチャンネル）: 桝本をメンションして承認を求める。✅ で承認、❌ で却下（桝本のリアクションだけ数える）
  3. 30分ごとのジョブがリアクションを読み、反映する
- 承認 → 記録し、**LINE で承認されたことを、スタッフの元のメッセージを引用して知らせる**
  （時間がたつと返信できないため、プッシュ送信。月の無料枠を使う。同じ回に承認したものは、グループごとに5件ずつ1回の送信にまとめる。
  無料枠が足りなくなったら `[labor] approval_line_notice = false` で止められる）
- 却下 → 記録しない（DB に載せない）。LINE には知らせない。Slack に却下したことだけ残す
- **リマインド: 承認待ちのあいだは、依頼の Slack スレッドで毎日1回**（依頼の翌日から、毎日 10:00 以降の最初の回）。すべての勤怠の承認依頼が対象
- 承認されていない勤怠は給与に入らない。給与の確定（翌月10日 9:00）までに承認すれば、その人の給与を計算し直す。確定した後は依頼を閉じる（管理者が調整額で直す）

### 2-4. 同じ日の2回目の入力・訂正
- 同じ人・同じ営業日の入力がもう一度来たら、**後の入力で上書きする**（訂正として扱い、Slack に変更前後を出す）
- 訂正も承認待ちになる。承認されるまでは前の記録のまま。却下なら前の記録のまま
- 承認待ちのうちに同じ日の入力がもう一度来たら、前の依頼は取り下げ、後の入力の依頼を残す（同じ内容なら依頼を増やさない）
- 給与が確定した月の勤怠は、LINE からは変えられない（管理者が直す。§5-4）

## 3. 記録と通知（データの流れ）

```
LINE（@null 勤怠）→ webhook → Cloud Tasks → worker（解析・期限の判定・本人の特定）
   └ すべて → 承認待ち（Slack で桝本に依頼。毎日リマインド）
        ├ 承認 → Firestore（正本）→ Asana「勤怠」タスク ＋ Slack #null_staff-management（→ ポータル・給与）＋ LINE で承認の連絡
        └ 却下 → 記録しない
```
新しい Cloud Run・Cloud Scheduler は作らない（既存の worker と、30分ごと・毎日のジョブに足す）。

### 3-1. Slack（新チャンネル `#null_staff-management`。本人が作成して Bot を招待する）
1件ごとに投稿する: スタッフの本名、営業日、勤務時間（開始〜終了、h）、**その月の稼働時間の平均（その月の総時間 ÷ 稼働日数）**。承認の依頼もここに出す。

### 3-2. Asana（新プロジェクト「Bar null 勤怠」。1タスク ＝ 1人 × 1営業日。スタッフごとの管理のデータベース）
- タスク名: `本名 11/23（日）`

| 項目 | 型 | 内容 |
|---|---|---|
| スタッフ名 | テキスト | 本名（台帳に無ければ LINE の表示名） |
| 稼働日 | 日付 | 営業日（勤怠） |
| 稼働時間（h） | 数値 | 終了 − 開始 |
| 勤務開始 / 勤務終了 | テキスト | ISO 8601 |
| 売上 | 数値（円） | **その営業日の本人の売上**（§4）。伝票が後から入る・直ると更新する |
| 状態 | 選択 | 記録済み／対象外 |
| 記録ID | テキスト | `W-{YYYYMMDD}-{スタッフID}`（同じ人・同じ日は同じ ID ＝ 二重に作らない） |
| 店舗 | テキスト | 空 ＝ Bar null |
| Slackスレッド | テキスト | |

### 3-3. スタッフ台帳（新。勤務条件の置き場）
worker（給与の計算・Slack の平均）と画面の両方が読めるよう、Asana プロジェクト「Bar null スタッフ台帳」に置く（1タスク ＝ 1人）。

| 項目 | 内容 |
|---|---|
| 本名 | 画面・給与・Slack・勤怠タスク名の表示に使う |
| LINE名 | LINE の送信者とプロモーターフラグの名前は、これと照合する（空白・敬称を除いて比べる） |
| 区分 | スタッフ／プロモーター／管理者 |
| 入社日 | |
| 時給 | 円。変えるときは適用開始日も入れる。**適用開始日から新しい時給**（前の勤務は前の時給） |
| バック率 | % |
| LINE ID | 初めて照合できたときにシステムが記録する（表示名を変えられても同じ人と分かるように） |

- LINE名で照合できない人が勤怠を送ったら、台帳に仮の人を作り、承認待ちにしたうえで「台帳に無い人」として Slack で知らせる（台帳に足せば、過去の分もその人に付け替える）
- 台帳・勤怠・給与のプロジェクトは、**管理者2人（桝本・岡本）だけが見られる非公開プロジェクト**にする

## 4. 本人の売上と、伝票のプロモーターフラグ

### 4-1. 伝票の書式に1行足す（売上管理の改修）
```
@null
日付：10/10
顧客名：山田様
金額：100,000
プロモーターフラグ：〇〇
備考：なし
```
- 「プロモーターフラグ：」に名前があれば、その伝票は **プロモーター経由の売上** として記録する。無い・空なら付けない
- 伝票にプロモーター名を持たせ、Asana の伝票に「プロモーター」の項目を足し、Slack の伝票の通知にも出す（Asana からの復元でも戻す）
- 売上レポート（A）にも同じ値が渡る。プロモーターとスタッフの分け方と給与の計算は、スタッフ管理の側（B）で行う

### 4-2. 本人の売上の決め方（スタッフ管理）
- プロモーターフラグがある伝票 → そのプロモーターの売上
- 無い伝票 → 伝票を送った人（担当）の売上
- 未収を含み、取消を除く（売上レポートと同じ）。顧客組数 ＝ 伝票の件数。レンタルスペースは含めない
- 名前は台帳の LINE名 で照合し、本名で表示する

## 5. 給与

### 5-1. 計算式
```
給与 ＝ 時給 × 前月の勤務時間の合計 ＋ 前月の本人の売上合計 × バック率
```
- プロモーターは時給の部分が 0。端数: 勤務時間は分まで、給与は円未満を切り捨て
- 支払: 月末締め・翌月25日払い

### 5-2. いつ計算するか
| いつ | 何をする | 動かし方 |
|---|---|---|
| 翌月の第1水曜 17:00 | 全員の前月分を計算（状態: 計算済み） | 30分ごとのジョブが「第1水曜の17時を過ぎ、まだ計算していない」ときに1回だけ動く（17:00〜17:30） |
| 計算済み〜10日 9:00 | 前月の本人の売上合計か勤務時間が変わったら、その人だけ計算し直す | 伝票・勤怠の保存をきっかけに動く。定期的な見回りはしない |
| 10日 9:00 | 確定する | 30分ごとのジョブ（9:00〜9:30） |
| 確定後 | 自動では計算し直さない。売上が変わったら Slack で知らせる | 伝票の保存がきっかけ |

- 売上が変わる理由（どれもきっかけ）: 伝票の追加、金額の訂正、取消、担当・プロモーターフラグの変更
- 勤怠の変わる理由: 承認（遅れた入力・訂正を含む）、管理者の手動上書き

### 5-3. 給与の記録（新。Asana「Bar null 給与」。1タスク ＝ 1人 × 1か月）
対象月、区分、勤務日数、勤務時間、売上、時給の分、バック、調整額、給与、状態（計算済み／確定）、計算した日時、計算し直した履歴。

### 5-4. 確定した給与を変える
管理者だけ。給与のタスクの「調整額」と「理由」を Asana で入れる（非公開プロジェクトなので、管理者以外は触れない）。

## 6. 画面

### 6-0. ホームポータルとテナント
- ホームポータルを作り、そこから各レポートに切り替える
- テナントは2つ: **売上管理**（いまの売上レポート）と **コスト管理**（配下にスタッフ管理、仕入管理、その他コスト管理）
- 右上にテナント切替のプルダウンを置き、どの画面からでも切り替えられるようにする
- どの画面も、数字と割合が一目で分かる形にする

### 6-1. スタッフ管理（全体）
- 上: ダッシュボード。管理者を除くスタッフ・プロモーターが作ったその日時点の売上、そのコスト（その日時点の給与）、その割合
- 詳細: 勤務時間の平均、勤務日数の平均、時給の平均、バック率の平均。スタッフとプロモーターに分けた集計
- 下: スタッフ・プロモーター別の一覧（その日時点の勤務時間・勤務日数・売上・給与）。押すと個人の画面へ

### 6-2. 個人の画面
- 勤務条件: 本名、**LINE名**、区分、入社日、時給（適用開始日）、バック率
- 月ごとのセクション → 月の画面:
  - 上: 売上、コスト、売上 ÷ コスト、勤務時間の合計、勤務日数、顧客組数、AI の示唆
  - 下: 勤務日ごとの一覧（勤務日、勤務時間、売上）
- 給与の詳細（§6-3 と同じもの。どちらからも行ける）
- AI の示唆には、その人の売上・給与の数字を渡してよい（名前は記号に置き換える。2026-11-14 本人）

### 6-3. 給与画面
- 月を選ぶ → その月の一覧。スタッフ・プロモーターのセクションに分ける
- 列: 勤務日数、勤務時間、売上、給与（状態: 計算済み／確定、調整があれば印）。押すと個人の給与の詳細へ
