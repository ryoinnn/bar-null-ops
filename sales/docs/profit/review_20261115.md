## 直したもの（重大度の高い順）

### 1. コスト管理・利益の出し分けが効いていなかった（高。公開中の版からあった）
- 権限の判定（持ち主か Editor か）で、結果を待たずに真偽を見ていたため、常に「許可」になっていた。閲覧だけの人にも、コスト管理のメニューと売上管理の利益の欄が出ていた。
- 実際に数字が読めるかは、Asana の非公開プロジェクトのメンバーかどうかと db の rules に左右される（非公開の勤怠・給与・仕入・備品・固定費は、メンバーでなければ読めない）。
- 直し: 判定を `common.js` の `BN.canManage` 1 か所にして、結果を待つ。判定できないときは見せない。テストあり。

### 2. 読めなかったのに「0 円」「0 件」と表示していた（高）
- 5ページとも、Asana の応答の形が想定と違うと、エラーにせず空のデータとして扱っていた。2 ページ目だけ壊れると、途中までの合計がそのまま出ていた。
- 件数の上限（4,000〜6,000 件）で、黙って読み込みを打ち切っていた。項目名が Asana 側で変わると、全件が落ちる・「対象外」の除外や店舗の区別が効かなくなる、がエラーにならなかった。
- Slack のレンタルの通知も同じで、読めないと 0 件のまま「記録済み」になり、利益を断定していた。
- 直し: 読み込みを `BN.readAll` 1 つにした。応答の形が違う・10,000 件を超えた・必須の項目が無い、はどれも読み込みの失敗にし、その費用は「読めませんでした」、利益は「—」にする。エラーの文面は原因ごとに分けた（接続・許可・項目名など）。

### 3. 本番とテストが混ざる経路があった（高）
- 読み込みに「世代」が無く、環境や期間を続けて切り替えると、古い読み込みの結果が後から画面を上書きした。
  - 売上管理: テストの売上が、本番の週の控え（db の `weeks/prod_…`）に保存され、書き直されない経路があった。古い環境の費用が、新しい環境の売上に重なって利益が出る経路もあった。
  - スタッフ管理・仕入・備品消耗品: 「テスト」と表示されたまま、本番の台帳・商品マスタ・明細に書ける経路があった。
- 環境の保存先がページごとに別で（4 種類）、コスト管理はテスト、詳細のページは本番、という状態になりえた。売上管理は、テストを見ていることが画面に出なかった。
- 直し: 環境は `BN.env` 1 つ（全ページ共通）。テストの間は上部バーに「テスト用のデータ」と出す。読み込みは後から始めたものだけを反映する。切り替えたら、まず前の環境の数字と保存ボタンを消す。書き込みは、画面のデータを読んだ環境と今の環境が同じときだけ行う。

### 4. 時給だけを変えて保存すると、過去の勤務の時給と給与が書き換わった（高）
- スタッフ管理で、適用開始日を変えずに時給だけ保存すると、worker が同じ開始日の履歴を新しい額で上書きし、過去の勤務の「時給の額」と給与を計算し直していた（契約 §2-2「前の勤務は前の額」に反する）。
- 直し: 時給を変えるときは、適用開始日に今日を入れて確かめてもらい、2 回目の「保存」で送る。過去の日付にするとき・区分を「管理者」にするときも、1 回知らせてから送る。入力の検査（時給は 0 以上の整数、バック率は 0〜100、日付の形式）を足した。

### 5. 人件費の計算（中〜高）
- 当月（給与が「見込み」）の週・途中までの期間で、バック・調整を二重に日割りしていて、人件費が少なく出ていた（見込みは「その日時点の額」なのに、月の日数で割っていた）。給与の記録が始まる 12 月から起きる問題だった。
- スタッフID の無い記録があると、月全体の人件費で時給の分を二重に数える経路があった。「給与」が空の記録を、印なしで時給の分だけ（または ¥0）として数えていた。
- 直し: 日割りの分母を、見込みの月は今日までの経過日数にした。人の照合は「スタッフID → 同じ名前の ID → 名前」の順。「給与」が空の記録・給与の記録が無い人がいる月は「一部のみ」にする（契約 §2-5・§5 を先に直した）。

### 6. 「記録済み」の判定（中）
- 仕入（週 1 回の取り込み）は、先週までの分だけで「記録済み」になり、少ない仕入のまま利益を断定していた。取り込みが止まっても同じだった。
- 逆に、仕入の無い週・カードを使わなかった週は「未記録」になり、利益が出なかった。売上管理とコスト管理で判定が違っていた。
- 直し: 判定を `BN.coverage` 1 つにして両方で使う（契約 §5 の 1〜4）。いちばん新しい記録が、仕入 10 日・備品消耗品 14 日以上前なら「一部のみ」。前後に記録がある 0 件の期間は「0 円の記録済み」。画面に「記録は M/D まで」と出す。

### 7. 書き込みの安全（中）
- 保存の成否を「失敗の一覧が無ければ成功」で判定していたため、応答を読めないと、Asana は変わっていないのに「保存しました」と出た。保存の直後に 60 秒のキャッシュの古い値を読み、古い名前で上書きする経路があった。
- 備品消耗品: 区分を直すだけで「手動修正＝あり」になり同期から外れ、マネフォ側で明細が置き換わると二重に数える経路があった。NIGITA（仕入で数える）を理由の表示なしに戻せた。
- 商品マスタの一括保存: 別の人が先に直した商品を、手元の古い入力で上書きしえた。
- 直し: 書き込みを `BN.writeTasks` 1 つにした。全件の成功を確認できたときだけ「保存しました」。確認できないときはそう伝える。どの場合も、キャッシュを使わずに読み直して実際の状態を出す。区分の変更では「手動修正」を書かない（契約 §3b）。NIGITA の明細は戻せない。一括保存は、送る前に読み直して、先に直された商品は送らない。

### 8. AI に渡す数字（中）
- スタッフ個人の示唆に、時給・バック率と、割り算でそれが出る数字（時給の分・バック・勤務時間）を渡していた（名前は渡していない）。
- 売上管理の示唆で、利益・人件費の数字が、閲覧者も読める総評に混じらないことを、AI への指示だけに頼っていた。1 人だけ働いた期間は、人件費がその人の額と同じになる。
- 直し: 個人の示唆は、売上・給与の合計・勤務日数・顧客組数だけを渡す。店全体の給与は 3 人以上のときだけ。売上管理は、利益のデータを別の呼び出しにだけ渡す（総評の入力には入れない）。1 人だけの期間は、人件費と、引き算でそれが出る変動費・利益・損益分岐を渡さない。

### 9. 複雑さ・重複（中〜低）
- 同じものが複数のページにあった: プロジェクトの ID（最大 4 か所）、固定費の計算（2 ページ ＋ Python）、Asana の読み込みとページ送り（6 か所。上限もばらばら）、環境の保存、「今日」の計算（営業日と暦日が混在）。
- 直し: `common.js`（`window.BN`）を新しく作り、ID・環境・読み書き・固定費・営業日・記録ありの判定・権限の判定を 1 つにまとめた。各ページからは同じものを消した。テストは `sales/tests/js/common.test.mjs`（22 件）。決まりは契約 §1b。
- Python の `fixed.py` も、ポータルと同じ扱い（前後の空白を無視、適用開始月の形式違いは数えない）にそろえた。

### そのほか直したもの

- データが古いと分かる表示: 本番で、最後の伝票が 4 日以上前なら知らせる（売上管理・コスト管理）。
- 売上管理: 担当者別の集計が名前の空白の違いで人を分けていた。示唆の保存の失敗を黙って捨てていた。費用の読み込み中でも示唆を作れた。保存してあった期間の値が壊れていると画面が出なかった。
