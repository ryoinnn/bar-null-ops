## 2. 監視の観点と要件

### (1) GCP の外からの死活監視
- GitHub Actions のワークフロー `system-monitor`（`.github/workflows/system-monitor.yml`）が **15 分ごと** に次を叩く。
  - 売上（Bar null）`sales-webhook` の `GET /health`（新設。認証なし）
  - 福岡の売上 `sales-webhook` の `GET /health`（同じコード）
  - 福岡の `node-api` の `GET /api/health`（既存。本番）
- 判定（2 回続いたら通知。GitHub の定時実行は数分〜十数分遅れることがあるため）:
  | 結果 | 見出し |
  |---|---|
  | 応答の本文に `billing is disabled` | 【課金停止】（観点 2） |
  | 10 秒で応答なし、または 5xx | 【停止】サービスが応答しない |
  | `/health` の `jobs.reconcile` が 75 分より古い（福岡は tick が 75 分より古い） | 【定期処理の停止】Scheduler・worker・連鎖の停止 |
  | `jobs.daily` が 26 時間より古い、`jobs.weekly` が 8 日より古い | 同上 |
  | デプロイの未反映（観点 3） | 【デプロイ失敗】 |
- `/health` は **状態と時刻だけ** を返す（金額・名前・URL・エラー本文は返さない）。Firestore の読みは結果を 60 秒覚えておき、連打されても増えない。
  - 返すもの: `ok`、`version`（デプロイしたコミットの短い ID）、`jobs`（reconcile / daily / weekly の最後の完了時刻）、`failing`（失敗が続いているステップ名だけ）
- 定期処理の完了時刻は、`jobs.run_steps` の最後に Firestore の `meta/heartbeat` に 1 回書く（30 分に 1 回の書き込み。無料枠に収まる）。
- **監視が止まったときの見張り（相互監視）**: worker の reconcile のステップ `monitor_watch` が、公開の GitHub API で
  `system-monitor` の定時実行を読む。3 時間以上動いていない、または続けて失敗している（Slack に出せていない）なら health が通知する。
  GitHub 側が止まっても GCP 側が、GCP 側が止まっても GitHub 側が気づく。
  （当初案の「/health が呼ばれた時刻を Firestore に書く」は、公開の webhook に書き込み権限が要るためやめた）
- `/health` が Firestore を読むため、sales-webhook に **`roles/datastore.viewer`**（読み取りだけ）を付ける（IAM の変更なので本人）。
- 監視先の URL は GitHub の Secrets（`MONITOR_TARGETS`）に置き、公開のコードやログに出さない。ログには「OK / 停止 / 課金停止」などの分類だけを出す。

### (2) 課金の状態
- 課金が止まると Cloud Run は本文 `The request failed because billing is disabled for this project.` の 500 を返す。
  (1) の外部監視がこれを見分け、**15〜30 分以内** に【課金停止】を通知する。GCP の認証は要らない。
- 通知文には、確かめるコマンド（`gcloud billing projects describe <project>`）と、再有効化後も反映に時間がかかることを書く。
- 予算アラートのメールは、請求先アカウントの管理者（本人）に届く（GCP の既定）。
- billing-guard の通知先も `#null_system-monitor` にする（予算との接続は特権管理者の作業待ちのまま。live 化は対象外）。
- **停止の原因（2026-11-15 判明。B）**: プロジェクトの**利用額上限（spend cap）**。10/28 に月の上限に達して停止、11/01 にリセット、11/13 に再び到達。billingEnabled は true のまま Cloud Run だけが「billing is disabled」を返していた。
  - 「達した」: 外部監視が 500「billing is disabled」で【課金停止】を出す（GCP の外。上の判定）。通知文に上限の確かめ方を書いた。
  - 「近づいた」: 予算の通知を使う。予算の金額を上限と同じにし、50%・90%・100% でメール（請求先アカウントの管理者＝本人）に届くようにする（請求の設定なので本人。Pub/Sub で Slack に出す経路は、組織の設定の解除待ちの billing-guard と同じ制約があるため、まずはメール）。
  - 上限をいくらにするか、何に費用が出ているかは本人と B が確認中。

### (3) デプロイ失敗（Cloud Build）
- `cloudbuild.yaml` で `GIT_SHA=${SHORT_SHA}` を worker と webhook の環境変数に入れる。`/health` の `version` で、今動いているコミットが分かる。
- 外部監視が GitHub の API で `main` の最新コミット（トリガーと同じく `sales/**` から `sales/report/**`・`sales/docs/**`・`sales/README.md` を除く）を調べる。
  そのコミットから **40 分たっても webhook の `version` が一致しなければ**【デプロイ失敗】を通知する（Cloud Build の画面へのリンクつき）。
  webhook はビルドの最後に入るので、一致すれば worker も成功している。
- Cloud Build の Pub/Sub 通知は使わない（課金が止まると一緒に止まるため）。即時性は 40 分以内で足りるとする。

### (4) LINE の取りこぼし防止
- **本人の操作**: LINE Developers のチャネル（Bar null の売上の Messaging API）で「Webhook の再送」と「エラーの統計集計」を有効にする。
- 二重処理の防止: 受け口はイベント ID（`webhookEventId`）から Cloud Tasks のタスク名を作っており、再送が来ても 1 件として処理される（`tasks.py`）。
  再送の受け付けと、同じイベントが 2 回届いても伝票が 1 件のままになることをテストで確かめる。
- LINE の再送には期限がある。長い停止（今回の 2 週間半など）は再送では戻らない。(1) の早期通知で停止を短くすることと、
  runbook の「取りこぼしの送り直し」（スタッフに再送を頼む）で補う。

### (5) ポータルで古いと分かる表示
- ポータル（`sales/report/portal/`）は A（#null_dev_sales-report）だけが編集する。ここでは仕様を決め、依頼文を渡す（`docs/monitoring_portal_request.md`）。
- 要件: 各ページで「最後の記録の日時」を出す。基準より古ければ警告の帯を出す。あわせて `#null_system-monitor` に未復旧の通知があれば「システム異常あり」の帯を出す。
  読み取りはポータルが既に使っている Asana / Slack のコネクタで行う（`/health` はポータルから読めない前提）。

### 外部 API 障害・認証切れ（GCP 内の既存の通知）
- `health.py` の【外部API障害 / 処理エラー】の投稿先を `#null_system-monitor` にする（dry_run のあいだは #test）。
  Square・マネフォ・Asana・Slack・LINE の 401（認証切れ・取り消し）もここに出る。
- 再通知は 6 時間を **8 時間** にし、最初の通知のスレッドに付ける（親の ts を `meta/job_health` に残す）。復旧もスレッドに書く。
- **認証切れ（401・403）は【認証切れ】として 1 回目から知らせる**（待っても直らず本人の作業が要る）。LINE の伝票の処理（process_event）の
  認証切れも対象（2026-11-10〜 Claude の APIキーが無効で 11/10・11/12 の伝票が処理されなかった。B の調査、2026-11-15）。
- LINE の処理が 10 回目でも失敗したときの通知（伝票の原文つき）は今のまま `#daily_barnull-sales` に出し、
  `#null_system-monitor` にも原文を除いて短く出す（公開チャンネルなので顧客名・金額は載せない）。

### 秘密情報の期限（2026-11-15 本人の依頼。B 経由）
- 11/10 からの伝票の失敗は、Claude の APIキーの有効期限（2026-11-09）切れが原因だった。期限は前もって分かっていた。
- `sales.toml` の `[[monitor.expiry]]` に鍵の名前・期限・更新手順を持ち、毎日のステップ `secret_expiry` が 30日前・7日前・前日・期限切れの
  時点で本人をメンションして `#null_system-monitor` に知らせる（各段階1回。ジョブが止まった日があっても次の回で知らせる）。
- 期限は秘密ではないので設定ファイルに日付で持つ。キー本体は持たない。期限の分からない鍵は本人に確認して足す。

### 第2段（PC 側。第1段の完了後に別途要件を詰める）
- 予約対応の常駐（PC）が、巡回の成功時刻を 30 分に 1 回 `sales-webhook` の `POST /heartbeat`（共有の合言葉つき）に送る。
  外部監視が古さを判定する（PC・常駐・ログインの停止が分かる）。
- 同じ仕組みで、仕入（週 1 回）の結果と、PC の `gcloud` 認証が切れていないかを送る。
- 予約対応のログイン切れの通知（今は `#notif_space-rent_null`）を監視チャンネルにも出す。

## 3. 通知の形
- 親: `<@U0A51TDCCEN> 【課金停止】売上（Bar null）: Cloud Run が「課金が無効」と応答しています（03:15 から）` と、確かめ方・runbook の節。
- スレッド: 8 時間ごとに「まだ続いています（経過 ◯時間）」。直ったら「【復旧】03:15〜05:40（2時間25分）」。親の先頭にも【復旧済み】を付ける。
- 状態（どの異常を通知中か、親の ts）は GitHub Actions のキャッシュに置く。消えても最悪で 1 回多く通知するだけ。
- Slack に投稿できなかったとき（トークン切れ・Slack 障害）は、ワークフローを失敗で終える。**GitHub から本人にメールが届く**（予備の経路）。

### 試験の結果（2026-11-15 JST）
| 観点 | 結果 |
|---|---|
