# Bar null 売上管理自動化システム 実装依頼

## 0. あなたへの依頼と進め方

あなたは株式会社0x0が運営する「Bar null」の売上管理を自動化するシステムを設計・実装するエンジニアです。
LINEグループに投稿される「伝票」を起点に、**Square決済との突合 → 銀行入金（マネーフォワード クラウド会計）の確認**までを自動で追跡し、各段階のステータスを **Slack（伝票ごとのスレッド）と Asana（伝票ごとのタスク）** に反映するシステムを構築してください。

進め方のルール:

- 一度にすべて作らないこと。§10 のフェーズ順に進め、各フェーズの終わりに「動作確認の結果」と「次のフェーズの計画」を報告し、私の承認を得てから次へ進むこと。
- 着手前に §12 の未決事項を私に質問すること。回答がない項目は本書の既定値で進め、その旨を明記すること。
- 外部サービス（LINE / Square / Slack / Asana / マネーフォワード / Google Cloud / Anthropic）の仕様は変わりうる。実装前に公式ドキュメントで最新仕様を確認し、本書の記述と食い違えば報告すること。
- 本番の Slack チャンネル・Asana プロジェクトへ書き込む前に、`DRY_RUN` とテスト用のチャンネル・プロジェクトで確認すること。
- トークン等の秘密情報をコード・リポジトリ・ログに含めないこと。
- **費用をかけない構成が最優先**（§7.1）。有料になりうる選択をする場合は事前に相談すること。

## 1. 背景

- Bar null：渋谷区代官山の完全予約制バー（1室貸切型）。運営は株式会社0x0。
- **営業日の定義：6:00〜翌6:00 を1営業日**とする（例：10/11 02:30 の会計は 10/10 営業日）。タイムゾーンは Asia/Tokyo。
- 会計の流れ：顧客ごとに対応終了時、担当スタッフ（顧客管理者）が LINE グループ「Bar null」に**伝票の写真**を投稿し、続けて**伝票の内容（日付・顧客名・金額・備考）をテキスト**で投稿する。伝票の下部に総額が記載されている。
- 決済：**すべての売上は Square に記録される**。
  - カード等：Square が決済手数料を差し引いた額を銀行口座へ振り込む（Square の「入金（payout）」）。
  - 現金：Square に現金決済として記録されるが、現金は直接銀行に入金されるため手数料はかからない（Square の振込には含まれない）。
- 銀行口座の入出金は、マネーフォワード クラウド会計（以下「マネフォ」）で確認する。
- 伝票（売上）の台帳は Asana（0x0.co.jp アカウント）、通知は Slack。

## 2. ゴール（完了の定義）

1枚の伝票について、次の3つが揃ったときに初めて「完了」とする。

1. 伝票（画像＋内容メッセージ）が登録されている
2. Square の決済額が、伝票の金額（未収分を除いた額）と一致している
3. その決済の入金（カードは手数料控除後の Square 振込、現金は全額）が銀行口座に着金したことをマネフォで確認できた

未収入金がある場合は、さらに**未収分の回収と銀行着金**を確認するまで完了にしない。完了した伝票は、Slack スレッド・Asana タスクともに以後更新しない。

## 3. アーキテクチャ（確定事項）

### 3.1 LINE の取得方式

LINE の画面をブラウザ操作する方式は**採用しない**（常時起動PCとログイン維持が前提で、ログアウトや画面変更で止まりやすいため）。
代わりに **LINE Messaging API の Bot（無料プランの LINE公式アカウント）をグループ「Bar null」に招待し、Webhook で画像・テキスト・送信者IDを受信**する。

### 3.2 構成

```
LINEグループ「Bar null」
   │ Webhook（画像 / テキスト / 送信者 userId）
   ▼
Cloud Run（Python / FastAPI, min-instances=0）
   ├─ POST /webhook/line        署名検証 → 生イベント保存 → Cloud Tasks に投入 → 即 200
   ├─ POST /tasks/process-event 伝票判定・抽出（Claude API）・ペアリング・起票
   ├─ POST /jobs/reconcile      Cloud Scheduler 30分毎：Square突合・入金照合・ペアリング期限切れ処理・Asana手動上書きの取り込み
   └─ POST /jobs/daily          Cloud Scheduler 毎日10:00 JST：未収リマインド・入金遅延アラート
   │
   ├─ Firestore        伝票の状態（正本）
   ├─ Cloud Storage    伝票画像の原本（非公開バケット）
   └─ Secret Manager   各種トークン
   ▼
Slack（通知・スレッド） / Asana（台帳・証跡） / Square API / マネフォ API / Claude API
```

### 3.3 技術選定

- 言語：Python 3.12、FastAPI。パッケージ管理は uv（または poetry）。祝日判定は `jpholiday` 等。
- インフラ：Google Cloud（Cloud Run / Cloud Tasks / Cloud Scheduler / Firestore / Cloud Storage / Secret Manager）。リージョンは `asia-northeast1` を基本とし、無料枠の条件次第で調整。
- 構築手順：Terraform か gcloud スクリプトのどちらか軽い方。手作業が必要な手順は README に必ず残す。
- 画像・テキスト解析：Claude API（Anthropic SDK）。構造化出力（JSON スキーマ / tool use）で受け取り、スキーマ検証する。
- **状態の正本は Firestore**。Slack と Asana は表示先であり、状態判定には使わない（例外：§5.7 の手動上書きフィールドの読み取り）。
- 外部連携は差し替え可能なインターフェースで抽象化する：`MessageSource`（LINE）, `PaymentSource`（Square）, `BankLedgerSource`（マネフォ）, `Notifier`（Slack）, `TaskTracker`（Asana）, `Extractor`（Claude）。特にマネフォは取得方式が変わる可能性が高い（§6.5）。
- 開発中の調査には Claude に接続済みの MCP（Square / Slack 等）を使ってよいが、本番コードは各サービスの API トークンで動かすこと。

## 4. データモデルとステータス

### 4.1 伝票（Slip）— Firestore `slips/{slip_id}`

| 区分 | フィールド |
|---|---|
| ID | `slip_id`（例 `S-20261010-001`） |
| LINE | `group_id`, `image_message_ids[]`, `text_message_ids[]`, `sender_line_user_id`, `sender_display_name`, `sent_at` |
| 画像 | `gcs_uris[]`, `sha256[]` |
| 抽出結果 | `from_image{business_date, total_amount, confidence}`, `from_message{business_date, customer_name, amount, note, raw_text}` |
| 確定値 | `business_date`, `business_date_source`（message / image / inferred）, `customer_name`, `slip_amount`, `note` |
| 未収 | `unpaid_amount`, `unpaid_remaining`, `unpaid_status`, `unpaid_due_date`, `collection_reports[]` |
| Square | `expected_square_amount`, `payment_ids[]`, `tender_types[]`, `gross_total`, `fee_total`, `net_total`, `match_method`, `matched_at` |
| 入金 | `expected_deposits[]{kind: square_payout / cash / unpaid_collection, amount, payout_id, expected_date}`, `deposit_matches[]{source_id, date, amount, description}` |
| 状態 | `status`, `status_history[]{from, to, at, reason}`, `alerts[]{type, message, at, resolved_at}`, `closed_at` |
| 連携先 | `slack{channel_id, thread_ts, permalink}`, `asana{task_gid, url}` |
| リマインド | `next_reminder_at`, `reminder_count` |

補助コレクション：

- `line_events/{webhookEventId}`：生イベント（冪等性の担保。30日で削除）
- `pending_messages`：ペアリング待ちの画像・テキスト
- `payment_claims/{square_payment_id}` → `slip_id`：1つの決済を2つの伝票に割り当てない
- `deposit_claims/{source_id}` → `slip_ids[]`：1つの入金の二重消し込み防止
- `staff/{line_user_id}`：表示名・Slack user ID・Asana user gid。初回投稿時に自動作成し、Slack/Asana との紐付けは手動で設定

> **送信者の紐付け（重要）**：伝票には必ず LINE の送信者（userId と表示名）を保持すること。伝票と内容メッセージは顧客の担当者が送るため、将来の**個人別売上管理のキー**になる。

### 4.2 ステータス

指定された4状態（起票済み / 決済確認済み / 入金確認完了 / 未収入金有）のうち、「未収入金有」は進捗と同時に成り立つ（例：決済確認済み かつ 未収あり）。そのため**進捗ステータスと未収ステータスを別の軸で持つ**。

進捗ステータス `status`：

| 値 | 意味 | 遷移条件 |
|---|---|---|
| 起票済み | 伝票登録・Slack通知・Asana起票が完了 | 伝票画像＋内容メッセージのペアが確定（または期限切れで片方のみ起票） |
| 決済確認済み | Square の決済額が期待額と一致 | §5.3 の突合に成功 |
| 入金確認完了 | 期待される入金がすべて銀行に着金 | §5.4 の照合に成功 |
| 要確認 | 自動判定できない／アラート発生中 | §5.6 の各アラート。解消したら元の進捗に戻す |

未収ステータス `unpaid_status`：

| 値 | 意味 |
|---|---|
| なし | 未収なし |
| 未収入金有 | 未回収 |
| 回収報告済み | LINE 等で回収の報告はあったが、着金は未確認 |
| 回収入金確認済み | 未収分の着金を確認済み |

**完了条件**：`status = 入金確認完了` かつ `unpaid_status ∈ {なし, 回収入金確認済み}`。
完了時は Asana タスクを完了にし、Slack スレッドに完了を投稿し、`closed_at` を記録する。

## 5. 機能要件

### 5.1 F1：LINE 受信・伝票判定・保存

1. 設定値 `LINE_GROUP_ID` のグループのイベントだけを処理する。他のトーク・1対1トークは無視する。
2. Webhook は署名（`X-Line-Signature`）を検証し、`webhookEventId` で冪等化する。再送（`deliveryContext.isRedelivery`）でも二重処理しない。
3. **画像メッセージ**：コンテンツ取得 API で即座に画像を取得し（LINE 側の保存期間は有限）、Claude API で次を判定・抽出する。
   - 伝票か否か（`is_slip`, `confidence`）
   - 伝票下部に記載の総額
   - 伝票に記載の日付（あれば）
   - 伝票でない画像は保存せず、メタ情報のみログに残す。確信度が閾値未満なら Slack に「伝票か判定できない画像」として確認を依頼する。
   - 伝票なら Cloud Storage に保存（`slips/YYYY/MM/{slip_id}_{n}.jpg`）。sha256 で同じ画像の再投稿を検知する。
   - 複数枚の画像（imageSet）で1枚の伝票を構成するケースに対応する。
4. **テキストメッセージ**：Claude API で種別を分類し、構造化する。
   - `slip_content`：伝票の内容（日付・顧客名・金額・備考）。備考からは未収額・回収予定日・支払方法のヒントも抽出する（例：「4万円未収」→ `unpaid_amount = 40000`）。
   - `correction`：直前の伝票の訂正（例：「さっきの山田様、95,000でした」）
   - `unpaid_collection_report`：未収の回収報告（例：「山田様の未収4万、振込ありました」）
   - `other`：雑談など。無視する。
   - 送信者の表示名はグループメンバーのプロフィール API で取得し、`staff` にキャッシュする。
5. **ペアリング（伝票画像 ⇔ 内容メッセージ）**
   - 原則：**同じ送信者**の「伝票画像 → 内容メッセージ」を1セットとする。
   - 画像の後 `PAIRING_WINDOW_MIN`（既定30分）以内に届いた同じ送信者の `slip_content` を紐付ける。テキストが先に来て直後（`TEXT_BEFORE_IMAGE_MIN`、既定5分以内）に画像が来るケースも許容する。
   - 間に他のスタッフの投稿が挟まっても、送信者で区別して正しく紐付ける。
   - 同じ送信者がペア待ちの画像を複数持つ場合は投稿順に対応させる。曖昧なら「要確認」とする。
   - 期限内に内容メッセージが来なければ画像の情報だけで起票し「内容メッセージ未着」アラートを出す。内容メッセージだけで画像が来ない場合も同様に起票し「伝票画像未着」アラートを出す。
6. **値の確定ルール**
   - 金額：画像の総額とメッセージの金額が一致すれば確定。不一致ならメッセージの値を暫定採用して「金額不一致」アラートを出す（Square 突合では両方の値で候補を探し、一致した方を報告する）。
   - 営業日：メッセージ ＞ 画像 の優先順。両方なければ「日付なし」とし、§5.3 の遡り検索を行う。メッセージと画像で日付が食い違えば要確認。
   - 年が省略された日付は、送信日時から見て最も近い過去の日付として解釈する（未来日にはしない）。

### 5.2 F2：起票（Slack 通知・Asana 登録）

ペアが確定したら次を行う。

1. **Slack**：売上チャンネルに**伝票ごとの親メッセージ**を投稿する。以降の更新はすべてこのスレッドへの返信で行う。
   - 内容：伝票ID / 営業日 / 顧客名 / 伝票金額 / 備考 / 担当（LINE 送信者）/ 現在のステータス / Asana リンク。伝票画像はスレッド内に添付する（設定で ON/OFF）。
   - **未収がある場合は、親メッセージの冒頭に「【未収あり ¥40,000】」のように明示する。**
   - ステータスが変わるたびに、親メッセージ本文のステータス行も `chat.update` で書き換える（チャンネル上での一覧性のため）。
2. **Asana**：1伝票＝1タスクで起票し、**伝票画像を添付する（証跡）**。
   - タスク名：`10/10 山田様 ¥100,000`（未収があれば末尾に `［未収 ¥40,000］`）
   - カスタムフィールド：ステータス（起票済み / 決済確認済み / 入金確認完了 / 要確認）、未収（未収入金有 / 回収報告済み / 回収入金確認済み）、営業日、顧客名、伝票金額、Square決済額、決済手数料、入金予定額、入金日、未収残高、担当（LINE送信者）、伝票ID、Square payment ID、Slack スレッドURL
   - セクション：起票済み / 決済確認済み / 入金確認完了 / 要確認（ステータスに合わせて移動）
   - 説明欄：抽出結果、LINE の原文、処理履歴
   - Asana のプランでカスタムフィールドが使えない場合は、セクション＋タグ（「未収入金有」）＋説明欄の構造化テキストで代替する。
3. Slack の `thread_ts` と Asana の `task_gid` を Firestore に保存する。

### 5.3 F3：Square 決済との突合

- 対象：`location_id = L7SVX8VVWDQBX` かつ `status = COMPLETED` の payment。SPICE DRINK は必ず除外する。
- 期待額：`expected_square_amount = slip_amount − unpaid_amount`（未収分はその日の Square に記録されていない前提。前提と違うデータが出たら要確認として報告）。
- 金額は `total_money`（円・整数。JPY の最小単位は1円）で比較する。
- **検索期間**
  - 営業日が分かる場合：その営業日（D 06:00 〜 D+1 06:00 JST）
  - 分からない場合：**LINE 送信日時の営業日を含めて2営業日前まで遡る**（送信日時の営業日を Ds として、Ds−2 の 06:00 〜 送信日時）
  - 指定の営業日に見つからず、前後の営業日にだけ候補がある場合は自動確定せず「日付ズレ疑い」で要確認にする。
- **照合ロジック（優先順）**
  1. 未割当の決済1件で金額一致。Square の決済メモ・顧客情報に顧客名があれば最優先。
  2. 割り勘：近接した時刻（`SPLIT_PAYMENT_SPAN_MIN`、既定30分以内）の複数決済（最大 `SPLIT_PAYMENT_MAX` 件）の合計が一致。
  3. 候補が複数あって一意に決まらない場合は、候補一覧をスレッドに出して要確認にする（自動確定しない）。
- 一度割り当てた決済は `payment_claims` に記録し、他の伝票には使わない。
- 一致したら：`status = 決済確認済み`。決済ID・支払手段（カード / 現金など）・手数料（`processing_fee`）・差引額を記録し、スレッドに「決済確認済み」を返信して、Asana を更新する。
- **タイミングとアラート**：起票直後に1回突合し、見つからなければ `/jobs/reconcile` で再試行する。**LINE 送信から `PAYMENT_GRACE_MIN`（既定60分）を過ぎても見つからなければ「決済未確認」アラート**（会計を受領していない可能性）を出す。アラート後も `PAYMENT_RETRY_DAYS`（既定3日）は再試行し、見つかれば自動で解消する。
- 割り当て済みの決済に返金（refund）が付いたらアラートを出す。

### 5.4 F4：銀行入金の確認（マネフォ）

決済が確認できたら、支払手段ごとに「期待される入金」を作り、マネフォの入金と照合する。

- **カード等（Square 振込の対象）**
  - Payouts API で、その決済を含む payout を特定する（payout entries の `payment_id` から辿る）。payout の金額と着金予定日を取得する。
  - **注意：Square の振込は複数の決済を合算したもの**。1伝票の「決済額 − 手数料」で銀行入金を探すのではなく、**payout 単位でマネフォの入金と照合**し、一致したらその payout に含まれるすべての伝票を入金確認済みにする。
  - payout には、伝票のない決済・返金・調整、口座が同じなら SPICE DRINK の決済も含まれうる。照合は payout の金額そのもので行う。
  - Square の振込サイクル（日本）：三井住友銀行・みずほ銀行は翌営業日、それ以外の銀行は木曜〜水曜の売上を同じ週の金曜に合算振込。土日祝は翌営業日。入金先銀行は設定値 `SQUARE_PAYOUT_BANK_TYPE`。
  - Payouts API が日本のアカウントで使えない場合のフォールバック：振込サイクルから対象期間の決済の net（`total_money − processing_fee`）を合算して期待額を計算する。
- **現金**
  - Square 上の現金決済（手数料0）。銀行への入金は Square 経由ではなく、**全額が直接入金**される。
  - 営業日から `CASH_DEPOSIT_WINDOW_DAYS`（既定14日）以内の、Square 由来でない入金と金額で照合する。
  - 数日分の現金をまとめて入金するケースに備え、未照合の現金伝票の組み合わせの合計でも照合する。一意に決まらなければ要確認。
- **マネフォ側の照合条件**：対象口座（設定値 `MF_BANK_SUBACCOUNT`）への入金で、金額が一致し、日付が着金予定日の前1日〜後3営業日の範囲。Square の振込は摘要のパターン（設定値 `MF_SQUARE_DESCRIPTION_PATTERNS`。実データで確認して確定）で識別する。
- 一致したら：スレッドに「入金確認完了」（着金日・金額・合算の有無）を返信し、`status = 入金確認完了` にして Asana を更新する。完了条件を満たせば完了処理を行う（未収が残っていれば完了にしない）。
- 着金予定日から `DEPOSIT_GRACE_BIZDAYS`（既定3営業日）を過ぎても見つからなければ「入金未確認」アラートを出す。

### 5.5 F5：未収入金の管理・リマインド

- **検知**：内容メッセージの備考から未収額・回収予定日・回収方法を抽出する。抽出があいまいなら要確認。
- **明示**：起票時点から、Slack 親メッセージの冒頭と Asana タスク名に未収を明示する（§5.2）。
- **回収の検知**（いずれか）
  1. LINE グループの `unpaid_collection_report` を、顧客名と金額で未回収の伝票に照合する → `unpaid_status = 回収報告済み`。スレッドに報告者と内容を投稿する。
  2. マネフォで、顧客名義（カナ）の振込入金が未収額と一致 → `回収入金確認済み`。振込名義と顧客名の対応は Claude で判定し、確信度が低ければ要確認。
  3. 後日の Square 決済が未収額と一致（決済メモに顧客名がある等）→ 突合して決済を確認し、その決済の着金確認をもって `回収入金確認済み`。
  - 一部回収に対応する（`unpaid_remaining` を減らしていく）。
  - 現金で回収したという報告の場合は、その現金の銀行入金を確認するまで追跡する。
- **リマインド**：起票日から **`UNPAID_REMINDER_INTERVAL_DAYS`（既定7日）ごと**に、その伝票のスレッドへリマインドを返信する。担当者を Slack でメンションする（staff の紐付けがなければ店長をメンション）。内容は顧客名、未収残高、経過日数、現在の状況（未回収／回収報告済み・着金待ち）。
- **停止条件**：`unpaid_status = 回収入金確認済み`、または Asana で手動クローズされた場合（§5.7）。

### 5.6 F6：アラート一覧

アラートはすべて該当スレッドに返信する。重要なもの（★）は `reply_broadcast` でチャンネルにも表示し、店長をメンションする。Asana は `status = 要確認` にし、要確認セクションへ移動して説明欄に追記する。

| アラート | 条件 |
|---|---|
| ★決済未確認 | 猶予時間を過ぎても Square に一致する決済がない（未会計の可能性） |
| ★金額不一致 | 画像の総額 ≠ メッセージの金額、または Square の合計 ≠ 期待額 |
| 突合候補が複数 | 決済の候補が一意に決まらない |
| 日付ズレ疑い | 指定営業日の外にだけ候補がある |
| 内容メッセージ未着／伝票画像未着 | ペアリングの期限切れ |
| 伝票判定不能 | 画像の伝票判定の確信度が低い |
| 重複疑い | 同一画像、または同一（営業日・顧客名・金額）の伝票 |
| ★返金検知 | 割り当て済みの決済に返金 |
| ★入金未確認 | 着金予定日から猶予を超過 |
| 完了後の訂正 | 完了済みの伝票への訂正メッセージ（自動で再オープンしない） |
| 外部API障害 | 連続失敗。Slack に通知できない場合はログと Cloud Monitoring で検知 |

### 5.7 手動対応（MVP）

自動判定できないケースに備え、Asana のフィールドで人が状態を上書きできるようにする（`/jobs/reconcile` が読み取る）。

- 「手動：決済確認済み」「手動：入金確認済み」「手動：未収回収済み」「手動：対象外（取消）」
- 上書きを検知したら、Slack スレッドにその旨（誰が・いつ）を投稿し、状態を進める。
- Slack のボタン操作による承認は後続フェーズの任意機能とする。

### 5.8 訂正

- `correction` メッセージは、同じ送信者の直近（`CORRECTION_WINDOW_HOURS`、既定24時間以内）の未完了の伝票に適用する。対象が曖昧なら要確認。
- 変更内容（変更前 → 変更後）をスレッドに投稿し、Firestore と Asana を更新する。必要なら Square 突合をやり直す（割り当ての解除を含む）。

## 6. 外部連携の仕様メモ（実装前に最新の公式ドキュメントで再確認すること）

### 6.1 LINE Messaging API

- 社内 Bot 用に、LINE公式アカウント（無料プラン）を新規作成して Messaging API を有効化する。今後開設予定の顧客向けアカウントとは分ける。
- 設定：Webhook ON、Webhook の再送 ON、「グループ・複数人トークへの参加を許可」ON、応答メッセージ・あいさつメッセージ OFF。
- グループ「Bar null」に Bot を招待する（**招待前の投稿は取得できない**）。
- 受信に費用はかからない。LINE へのメッセージ送信は原則行わない。任意機能として「伝票を受け付けました」を reply API で返す機能を用意し、既定は OFF とする。
- 送信者の表示名：`GET /v2/bot/group/{groupId}/member/{userId}`
- 画像の取得：`GET https://api-data.line.me/v2/bot/message/{messageId}/content`
- ユーザーの同意状況によってはイベントに `source.userId` が含まれないことがある。その場合は「送信者不明」として処理を続け、要確認にする。

### 6.2 Square API

- 自社マーチャントの本番 Personal Access Token を使う（OAuth アプリは不要）。
- 使うAPI：Payments（ListPayments / GetPayment）、Refunds、Payouts（ListPayouts / ListPayoutEntries）、Orders（メモ・明細の補助）、Locations。
- 必要な権限：`PAYMENTS_READ`, `ORDERS_READ`, `PAYOUTS_READ`, `MERCHANT_PROFILE_READ`
- 支払手段は `payment.source_type` で判定する（CARD / WALLET 等 → 振込対象、CASH / EXTERNAL → 振込対象外）。Phase 0 で実データを見て確定すること。
- 時刻は UTC で返るので JST に変換し、営業日に換算する。

### 6.3 Slack

- Slack App を作成し Bot トークンを使う。スコープ：`chat:write`, `files:write`, `users:read`（チャンネル作成も自動化するなら `channels:manage`）。
- 新規チャンネル（案 `#barnull-sales`）を作成し、Bot を招待する。
- 無料プランでは90日より古いメッセージが閲覧できなくなる点に注意。状態の正本は Firestore、台帳は Asana とする。

### 6.4 Asana

- **0x0.co.jp のアカウントで** Personal Access Token を発行する（現在 Claude に接続されている Asana は別会社のアカウントなので使わない）。
- プロジェクト・セクション・カスタムフィールドはセットアップスクリプトで冪等に作成する。
- 画像の添付：`POST /attachments`（parent = task_gid）
- カスタムフィールドが使えないプランの場合は §5.2 の代替手段を使う。

### 6.5 マネーフォワード クラウド会計（最重要リスク：要調査）

- 公開 API あり（OAuth2。認可 `https://api.biz.moneyforward.com/authorize`、トークン `https://api.biz.moneyforward.com/token`）。アプリ登録には「システム管理」と「アプリ開発」の権限が必要。1アプリでアクセスできる事業者は1つ。クラウド会計の利用者は追加料金なし。
- 公開情報で確認できた範囲では、**仕訳の参照（`journal.read`）はできるが、連携口座から取り込んだ未仕訳の入出金明細を「読む」APIは確認できていない**（明細は作成・更新の記載のみ）。
- そのため Phase 0 で次を調査し、方式を決めて報告すること。
  1. 連携口座の明細を読める API があるか（あれば第一候補）
  2. ない場合は、仕訳 API で「対象口座（普通預金）の借方＝入金」を読む方式。この方式では、明細が仕訳として登録されるまで入金を確認できないため、銀行明細を仕訳に登録する頻度と、自動仕訳ルール等で即時に登録できるかをユーザーに確認する
  3. どちらも難しい場合は、費用ゼロを前提に代替案を提案する（例：銀行の入金通知メールを Gmail API で読む、マネフォの CSV を定期的に Drive に置いてもらう 等）
- リフレッシュトークンは Secret Manager に保存し、更新時に上書きする。スコープは最小限にする（`journal.read`, `accounts.read`, `connected_account.read` などを調査のうえ確定）。

### 6.6 Claude API

- 用途：伝票画像の判定・抽出、テキストの分類・抽出、振込名義と顧客名の対応判定。
- 費用を抑えるため、まず低コストのモデル（Haiku クラス）で処理し、確信度が低いときだけ上位モデルで再判定する。モデル名は設定値にする。
- 出力は JSON スキーマで厳密に検証する。失敗したら1回リトライし、それでも失敗すれば要確認にする。
- プロンプトには「推測で埋めない（読めない値は null にする）」と明記する。
- 画像は送信前に適切な解像度へ縮小する（費用と読み取り精度のバランスを実測で決める）。

## 7. 非機能要件

### 7.1 費用（最優先）

- **月額ほぼ0円**を目標とし、各サービスの無料枠だけを使う。
  - LINE公式アカウント：無料プラン（受信のみ）
  - Google Cloud：Cloud Run（min-instances=0）、Cloud Tasks、Cloud Scheduler（ジョブ数は無料枠に収める。本書の構成では2本）、Firestore、Cloud Storage、Secret Manager を無料枠内で使う。**最新の無料枠の条件を確認**し、超えそうな設計は相談すること。
  - 請求先アカウントに予算アラート（例：¥500）を設定する手順を README に書く。
  - 従量課金は Claude API のみ。伝票1枚あたりの費用を実測して報告すること。
- 常時起動インスタンス、Cloud SQL、有料の監視サービスは使わない。

### 7.2 信頼性・冪等性

- すべての処理を冪等にする。同じイベントや同じジョブを再実行しても、二重投稿・二重起票・二重消し込みをしない。Slack / Asana に書き込む前に Firestore の状態を確認し、書き込み結果のIDを保存する。
- 外部 API 呼び出しは指数バックオフでリトライする。Square / Asana / Slack のレート制限を考慮する。
- ジョブが途中で落ちても、次回の実行で回復できること。

### 7.3 セキュリティ・個人情報

- 秘密情報は Secret Manager に置く。リポジトリには `.env.example` だけを含める。
- Cloud Run の `/tasks/*` と `/jobs/*` は認証必須（OIDC）。`/webhook/line` は署名検証で守る。
- 顧客名と金額はログに出さない（`slip_id` で追跡する）。画像バケットは非公開にする。
- 保持期間：生イベントは30日で削除する。伝票画像とデータの保持期間は設定値とし、既定は無期限（会計上の保存要件をユーザーに確認）。

### 7.4 時刻

- 内部は UTC で保持し、表示と営業日判定は Asia/Tokyo で行う。営業日の境界（06:00）は設定値にする。

### 7.5 運用

- Cloud Logging に構造化ログを出す。
- 再処理用の CLI を用意する（特定の伝票の再突合、日付範囲の再照合、DRY_RUN での再生）。
- 任意機能：毎日の処理件数・未解決アラート数のサマリーを Slack に投稿（既定 OFF）。

## 11. テスト・受け入れ基準

ユニットテスト（必須）：

- 営業日換算（05:59 → 前営業日、06:00 → 当日、年の補完、月末・年末・祝日）
- ペアリング（同じ送信者、投稿順、他スタッフの割り込み、期限切れ、テキスト先行）
- Square 突合（単一一致、割り勘、候補複数、日付なしの遡り、SPICE DRINK の除外、割り当て済みの除外、未収の控除）
- 入金照合（payout の合算、現金1件、現金のまとめ入金、祝日をまたぐ振込）
- 状態遷移（全遷移、完了条件、完了後の訂正）
- 冪等性（同じ `webhookEventId` の再送、ジョブの二重実行）

外部 API はモックし、LINE Webhook の fixture を使って DRY_RUN で通しテストを行う。

受け入れシナリオ：

1. 通常：伝票＋内容 → 起票 → Square 一致 → 入金確認 → 完了（Slack は1スレッドで完結、Asana タスクは完了）
2. 未収：10万円のうち4万円が未収 → 親投稿に未収を明示 → 6万円で Square 一致 → 7日後にリマインド → LINE で回収報告 → 振込の着金 → 完了
3. 未会計：Square に該当がない → 猶予後に決済未確認アラート
4. 日付なしの伝票：2営業日遡って一致
5. 割り勘：3枚のカードの合計で一致
6. 現金：現金決済 → 銀行への現金入金で完了
7. 伝票でない写真 → 無視される
8. 画像とメッセージの金額不一致 → 要確認

## 12. 着手前にユーザーへ確認すること

1. Square の入金先銀行（三井住友・みずほ／それ以外）と、Bar null と SPICE DRINK の入金口座が同じかどうか
2. マネフォ：銀行口座の連携状況、明細を仕訳に登録する頻度と担当（税理士か社内か）、対象口座の勘定科目・補助科目名、API アプリを登録できる権限者
3. 現金の銀行入金のやり方（毎回か、まとめてか、誰がいつ行うか）
4. 割り勘（複数カード）の頻度と、Square で決済するときに決済メモへ顧客名を入れる運用ができるか（入れられると突合の精度が大きく上がる）
5. 未収が後日 Square で決済されることはあるか（振込のみか）
6. Asana：0x0.co.jp ワークスペースのプラン（カスタムフィールドの可否）、プロジェクトを置くチーム、閲覧するメンバー
7. Slack：使用するワークスペース、アラートでメンションする人、LINE の送信者と Slack ユーザーの対応表
8. 伝票のサンプル画像と内容メッセージの実例（10件程度。テスト用。個人名はマスクしてよい）
9. Google Cloud：0x0 の GCP プロジェクトと請求先アカウントを使えるか（無料枠の利用でも請求先アカウントの登録が必要）。使えない場合は Google Apps Script での構成への切り替えを検討する
10. 社内 Bot 用の LINE公式アカウントを新規作成してよいか
11. 伝票画像とデータの保存期間

- スタッフ向けの1枚ガイド（内容メッセージの推奨フォーマット、訂正・回収報告の送り方）。推奨フォーマットの例：

```
日付：10/10
顧客名：山田様
金額：100,000
備考：40,000未収（10/17振込予定）
```

※ 自由記述でも解析できるようにするが、このフォーマットで送ってもらうと精度が上がる。
